## 1. 背景与问题陈述

现有链路（pdf-parse-v3，Schema v3.0）已能完成：分诊（文本/扫描/混合）→ 引擎路由（PyMuPDF 版式 / RapidOCR / WinRT）→ 章/条/表题/图说结构化 → 逐页溯源 JSON [来源：SKILL.md、PDF解析输出JSON规范.md]。

三份既有文档分别揭示了三类未闭合的缺口：

| #   | 缺口                                                                | 证据出处                            | 性质                   |
| --- | ----------------------------------------------------------------- | ------------------------------- | -------------------- |
| G1  | **表格结构缺失**：扫描件表格只有 caption，单元格数据未重建；JSON 中无 rowspan/colspan/网格坐标  | 视觉兜底修复-试点方案 §1、§4；结构保真研究报告 §1.4 | 信息重建问题（PDF→JSON 段断裂） |
| G2  | **图只有"说"没有"体"**：figures 仅存图说文字，图的本体（像素）没有文件化入库，无法原位还原显示           | 结构保真研究报告 §5                     | 信息承载不完整              |
| G3  | **无下游保真出口**：JSON 之后没有标准化的 MD/HTML 序列化；朴素拼管道表必然把复杂表"读错"（数字与列名静默错位） | 结构保真研究报告 §1.2、§2.2              | 表达能力问题（JSON→MD 段断裂）  |

前沿侧（2026 年）文档解析能力已发生代际跃迁：0.9B–1.2B 的专用文档 VLM 在 OmniDocBench v1.6 上达到 95.15–96.33 综合分（3B 的 dots.ocr 为 90.77），表格 TEDS 最高 94.76，且在扫描、倾斜等真实劣化场景显著优于通用大模型 [来源：见 §5]。这意味着"局部视觉兜底"与"表格结构重建"两条路线都有了更成熟的外部参照系与可选引擎。本团队 2026-09-06 的对拍与整册补测进一步证实：GLM-OCR（智谱 API）在真实规范扫描册上达到整册 100% 成功率、表格零漏检、86.3% 结构守恒直通、单册成本 ¥0.1615 的水平，已具备作为主解析器的工程条件 [来源：《视觉与文档解析API对拍测试报告》v1.1 §3/§7]。

## 2. 第一性原理锚点

### 2.1 锚点陈述（不可让渡）

**系统的唯一使命：把任意 PDF 承载的信息，完整、忠实、可溯源、可还原地转移到机器可消费（JSON）与人可阅读（MD/HTML，按需）的形态。**

推论（与 v3.0 规范 §0 一致并扩展）：

1. PDF 一页的信息形态只有三类：**文字、表格、图**。任何一类在某环节断供，都是系统级缺陷。
2. 无损链路的充要条件（信息论）：**中间表示的表达力 ≥ 源文档结构复杂度**，且每个转换器在其表达力范围内做保真映射 [来源：结构保真研究报告 §1.3]。
   - 对表格：网格模型（n_rows × n_cols + 每格 row/col/rowspan/colspan/text/bbox/角色）是与 HTML 表格表达力等价的**最小完备模型**，必须作为 JSON 层的表格基准表示。
   - 对图：图本体是位图，"解析其内容"不是表达问题而是重建问题；保真的做法是**整体切出、文件化、JSON 只存索引**。
3. 忠实优先于结构：**解析失败时保留原文并诚实标记，禁止为凑结构而错拆、禁止静默覆盖原文**（继承公理 A1 忠实性 / A2 无损性 / A5 诚实性）。
4. 可溯源（A6）：任何结构化元素可双向定位（内容 ↔ 物理页 ↔ 页内坐标）；坐标链必须在各表示间确定可换算。

### 2.2 从锚点推导的需求方向

| 锚点推论                    | 对应需求域                    |
| ----------------------- | ------------------------ |
| 表格必须表达合并与网格             | §7-C 表格结构重建；§8 数据模型升级    |
| 图必须文件化并可原位还原            | §7-B4/B5 图片抽取与索引         |
| 下游表达力必须分级匹配             | §7-F MD/HTML 分级序列化（按需生成） |
| 重建必然有不确定性，必须可观测、可校验、可标记 | §7-D 视觉兜底、§7-E 校验闭环      |
| 溯源需要坐标贯通                | §7-B1/B2/B3 行级坐标与变换登记    |

## 3. 控制论系统观（需求组织的第二根轴）

把整条链路视为一个**被控对象 = 信息保真度**的反馈控制系统：

| 控制论角色        | 系统中的对应物                                         | 需求含义                                                    |
| ------------ | ----------------------------------------------- | ------------------------------------------------------- |
| 前馈控制         | **分诊**（先测后读，按承载形态选引擎）                           | 错误发生前选路；分诊信号必须显式、可复核（FR-A）                              |
| 传感器          | L1 规则/几何自检、L4 校验门（守恒/缺陷签名/交叉对位三信号）       | 全部 0-token、确定性、可复算；传感先于执行（FR-D1/E）                      |
| 控制器          | 四层降级链的路由决策                                      | 总是先走成本最低且充分的手段；升级条件显式（FR-D）                             |
| 执行器          | 文本引擎 / **GLM-OCR 整页解析（扫描主通道）** / 本地 OCR（校验通道，默认开启） / 几何重建 / 第二意见视觉模型 | 执行器多样性由显式路由表容纳（FR-A2）；可替换接口的抽象为延后项（Q2/Q5 裁决，本期不实装）      |
| 反馈与校正        | 校验 → 一次定向重试 → 标记                                | 校正有界（限次重试，FR-D8），防震荡                                    |
| 安全态          | **诚实标记 + 原文保留**                                 | 任何失败收敛到安全态而非猜测态；下游协议强制（FR-E5/E6）                        |
| 必要多样性（Ashby） | 文档形态多样性（文字/扫描/混合 × 线框表/三线表 × 简单/复杂合并）必须由引擎多样性匹配 | 不为单一引擎写死流程；路由表显式（FR-A2、§7-C/D）；多样性可后置扩展（Q5 裁决：重型引擎仅留接口） |
| 可观测性         | 修复报告、失败清单、token 台账                              | 每表留痕：路径、结果、token、校验项（FR-G、§9）                           |

### 4.3 现状关键缺口（实证定位）

> 以下三条是对现状代码行为的实证核查结果，**均为可修复缺陷**，本次升级即修复；列出仅为给修复需求提供证据锚点。

1. **OCR 行级坐标正在被丢弃**：rapid_ocr_pages.py 排序后只取 `r[1]` 文本，RapidOCR 原生返回的四点 box（`r[0]`）未入 JSON，导致"定位→裁剪"不闭环 [来源：rapid_ocr_pages.py L86–88；试点方案 §3-①]。
2. **v3 表格条目无数据**：扫描路径下 tables[] 仅 caption + note"单元格数据未重建" [来源：pdf2v3.py L254–262]。
3. **官方图片 token 估算不可作为预算依据**：试点实测单图 prompt_tokens 195–439（真实表 900×577 达 419–439，高于纯色图 800×800 的封顶值 431），而官方宣传"每张图片最多占 384 tokens"——两者矛盾，**以实测 usage 为准**并列为实现期验证项 [来源：试点方案 §3-⑤、§6.5；DeepSeek 官方新闻，见 §5.3]。

## 5. 前沿调研结论（2026-09-06 检索快照）

### 5.1 文档解析 SOTA 格局（OmniDocBench）

| 模型                          | 参数     | OmniDocBench 成绩         | 表格 TEDS                             | 部署形态                                                                     | 来源                                                                            |
| --------------------------- | ------ | ----------------------- | ----------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| PaddleOCR-VL-1.6            | 0.9B   | v1.6 综合 **96.33**（SOTA） | **94.76**；Real5 扫描场景 94.74、倾斜 92.66 | 开源；x64 CPU 可跑（慢），GPU 最低 RTX 3060 12GB                                    | [GitHub PaddleOCR][src-paddle]、[PaddleOCR-VL-1.6 评测综述][src-velog16]           |
| GLM-OCR                     | 0.9B   | v1.6 ≈ 95.15–95.22      | ≈92.83                              | 开源                                                                       | [Infinity-Parser2 技术报告综述][src-velog-inf]、[PaddleOCR-VL-1.6 评测综述][src-velog16] |
| MinerU2.5-Pro（MinerU 3.4.5） | 1.2B   | v1.6 ≈ 95.69–95.75      | 93.62                               | 开源 Apache-2.0；pipeline 后端 4GB 可纯 CPU（v1.6 仅 86.47），hybrid/vlm 需 ≥8GB GPU | [NexGPU 部署指南][src-nexgpu]、[OmniDocBench README][src-omni]                     |
| dots.ocr                    | 3B     | v1.6 ≈ 90.77            | 87.18                               | 开源                                                                       | [velog 综述][src-velog16]                                                       |
| DeepSeek-OCR-2              | 3B     | v1.5 91.09              | —                                   | 开源                                                                       | [百度百科·OmniDocBench V1.5][src-baike]                                           |
| Mistral OCR 4               | 商用 API | 自报 v1.6 93.07（独立复测口径不一） | —                                   | $4/1000 页（batch $2）                                                      | [Awesome Agents][src-awesome]                                                 |

要点：

1. **专用小模型已系统性超越通用大模型**：0.9B–1.2B 专用 VLM 在表格/公式/阅读序上全面压过 GPT-5.2、Qwen3-VL-235B、Gemini 3 Pro 等通用模型 [来源：[velog 综述][src-velog16]]。
2. **表格结构以 HTML/OTSL 输出已成工业共识**：PaddleOCR-VL（OTSL）、MinerU（HTML）、Docling（TableFormer→HTML）、PP-StructureV3（HTML）均原生输出含合并信息的表格结构 [来源：[PaddleOCR-VL 论文][src-arxiv-pov]、结构保真研究报告 §四-L1]。
3. **TEDS（树编辑距离相似度）是表格识别标准指标**；OmniDocBench v1.6 起采用 MGAM 自适应粒度匹配消除匹配偏差，并新增 296 页含复杂嵌套表的难例 [来源：[OmniDocBench README][src-omni]]。
4. **失败模式差异（对本系统设计至关重要）**：传统 OCR 失败是"看得见的错字"，VLM 失败是"编造（幻觉）"——因此凡 VLM 参与的环节必须配确定性校验与诚实标记 [来源：[MadeByAgents 2026 文档管线][src-agents]]。

### 5.2 对本系统的可行性含义

- 目标运行环境为**无 GPU 的单机 CPU**。PaddleOCR-VL 与 MinerU-vlm 在本机不可行或极慢（依据同 v1.0：[PaddleOCR 官方教程][src-paddle-doc]、[GitHub Issue #16823][src-paddle-issue]、[NexGPU][src-nexgpu]]）；**但 2026-09-06 实测证实：专用文档解析模型的云端 API 形态（GLM-OCR）在本机完全可用且廉价**（整册 ¥0.1615、单页 4.25s），v1.0 的主路线可行性约束已解除 [来源：对拍测试报告 §7]。
- 因此本系统的定位修订（Q11=A+ 裁决）：**扫描件以 GLM-OCR 整页解析为主通道；文字层 PDF 仍以本地确定性提取为第一路径（零误差、零成本、零出域——让视觉模型读文字版截图是引入噪声的迂回）；本地手段（OCR 行级、几何重建、规则校验）整体转任校验与兜底通道；第二意见视觉模型（DeepSeek/Qwen）为缺陷阶梯的复核执行器**。控制论结构原则：执行通道可单一，观测与纠偏通道必须冗余且独立 [来源：架构思考 §2.3/§3]。
- 本地重型 VLM 仍仅留接口文档、本期不实装（Q5 裁决延续）。

### 5.3 视觉 API 格局（2026-09-06 实测后修订）

- **GLM-OCR（智谱，扫描件主解析器——Q11 裁决）**：0.9B 专用文档模型，`layout_parsing` 端点，图片/PDF 输入（单图 ≤10MB、PDF ≤50MB/100 页）；输入输出同价 ¥0.2/百万 tokens。实测：整册 180 页全成功、单页 prompt 3571–4554 tokens、单页均成本 ¥0.0009；输出 MD 内嵌 HTML 表格 + layout_details 块级 bbox/类型 [来源：对拍测试报告 §3/§5/§7；[智谱 GLM-OCR 文档][src-glmocr]]。
- **DeepSeek `deepseek-v4-flash-vision-exp`（第二意见/兜底复核）**：图片折算 token 计入输入；价格同 V4-Flash（输入缓存未命中 ¥3.0/百万 tokens 高峰、¥1.5 空闲；输出 ¥9.0/¥4.5；缓存命中 ¥0.10/¥0.05）；Files API 免费且同图可多请求复用；上下文 1M / 输出 384K；峰谷时段（工作日 9–12/14–18 高峰，周末全天空闲价）[来源：[DeepSeek 官方新闻][src-ds-news]、[新浪·DeepSeek 计费详解][src-ds-price]、[AIHub 模型页][src-aihub]]。**矛盾点（验证项 V-1，保留）**：官方"单图最多 384 tokens"与试点实测 419–439 不一致，以真实 usage 回填校准 [来源：试点方案 §3-⑤、§6.5]。
- **Qwen3-VL-Flash（阿里百炼，文本复核可用、结构场景不推荐）**：输入 ¥0.15/M、输出 ¥1.5/M（≤32K 档）；对拍实测文本词元命中 0.90–0.98，但网格结构 0/4 不守恒 [来源：对拍测试报告 §3/§4；[阿里百炼价格][src-bailian]]。

## 6. 总体目标与非目标

### 6.1 总体目标（一句话）

**任意 PDF（文字版 / 扫描版 / 混合）→ 可溯源结构化 JSON（文本 + 网格表格 + 图片索引三形态完备）+ 附件图片库；JSON 是默认唯一产物，Markdown（复杂表局部内嵌 HTML 表格）与 HTML 仅在用户明确要求时按 §7-F 生成；全流程全自动，失败诚实标记，成本可预算。**（Q3 裁决）

### 6.2 目标（In Scope）

1. PDF → JSON：三形态完备承载，表格升级网格模型，图片文件化入库并原位锚定。**默认产物到此为止。**
2. JSON → MD（按需，用户指令触发）：按表格复杂度分级序列化；图片原位引用。
3. JSON → HTML（按需，用户指令触发）：自包含可读页面（表格原生渲染、图片原位、溯源信息可查看）。
4. 表格结构重建与缺陷闭环：GLM-OCR 整页解析（扫描件主通道）→ HTML→网格适配 → 校验门（守恒/缺陷签名/交叉对位）→ 缺陷阶梯（规则修复 → 裁剪重译 → 第二意见复核 → 诚实标记）。
5. 质量与成本的可观测：修复报告、失败清单、token 台账、验收指标。

### 6.3 非目标（Out of Scope，显式排除）

1. 无框线且已完全失真的老扫描表 100% 还原（承认上限，以诚实标记收敛）[来源：试点方案 §1]。
2. 任何需要人工点选/交互的流程（全自动闭环；人工仅在失败清单层面事后介入）。
3. 本机 GPU 重型 VLM 的默认启用（仅留接口文档，本期不实装——Q5 裁决）。
4. 图的像素数据内联进 JSON（base64 内联明确禁止；图为文件 + 索引）[来源：研究报告 §5.5-4]。
5. 公式识别（LaTeX 化）、手写体、多语种（>中英）——本期不做，但数据模型不得堵死后续扩展。
6. RAG 切分、检索服务等下游应用本身（本系统只保证产物可被下游正确消费，含读取方协议）。
7. **MD/HTML 的主动生成**（Q3 裁决：无用户明确要求时不生成；生成能力内置待命）。

### Q1　Schema 版本策略：v4.0 重构 还是 v3.1 增量并存？【已裁决：A】

**术语**：`schema_version` 是写在 JSON 顶层的格式版本号，读取方（人或程序）按它决定用哪套规则解析。当前 v3.0 的表格是 `data: [[...]]` 二维数组——只能表达"几行几列、每格什么字"，**无法表达合并单元格**。新网格模型 `{n_rows, n_cols, cells:[{row,col,rowspan,colspan,text,bbox}]}` 才能完整表达合并、多级表头，与 HTML 表格表达力等价（研究报告 §1.1）。

- **选项 A：升 v4.0 重构**——表格条目改为网格模型，`data[][]` 列入废弃清单（旧文件仍可读，新文件不再生成）。
  - 优：单一事实源——每张表只有一种表示，校验规则只有一套，不会出现两份表示互相矛盾；与 HTML 双向无损互转。
  - 劣：版本号大跳，读取方要写"按版本分支"的逻辑；实现侧需一次性把表格读写路径换完。
- **选项 B：升 v3.1 并存**——保留 `data[][]`，旁边新增 `cells[]` 网格。
  - 优：旧读取方完全无感知；改动量小。
  - 劣：同一张表存两份表示，谁来保证它们永远一致？校验要查两套；文件体积变大；长期看是把技术债留给下游。
- **裁决：A**（2026-09-06）。理由：网格模型是表达力基准，`data[][]` 任何时候都能从网格退化生成（导出视图），没必要在 JSON 里常驻双份；兼容性已由"旧文件不强制迁移"保证（规范 §1.0 既定方针）。这符合第一性原理：表达力不足的旧表示应当退役，而非叠加。

### Q2　视觉兜底默认执行器：绑定 DeepSeek 还是抽象接口？【已裁决：A，接口抽象延后】

**术语**："执行器"= 实际干活的引擎（这里是视觉大模型 API）。"接口抽象"= 先定义一份统一契约（输入：表格截图+参考文本；输出：固定结构的 JSON），具体调哪家模型作为可插拔的实现。

- **选项 A：只接 DeepSeek**（`deepseek-v4-flash-vision-exp`，已实测：单表 prompt≈419–439 tokens、completion≈2940 字符，输入约 ¥0.001/图）。
  - 优：最快落地，实测数据齐全。
  - 劣：单一供应商绑定——该模型是实验性质（exp 后缀），下线/涨价/口径变更都会直接冲击链路（风险 R8）。
- **选项 B：抽象接口 + DeepSeek 作默认实现**，预留 GLM/Qwen 等其他视觉模型的接入位。
  - 优：抗供应商风险；"爆破表清单"日后可换更强模型定向重跑而不用改主流程。
  - 劣：多一层接口设计，工期略增。
- **选项 C：暂不接任何 API**，先交付"检测+定位+诚实标记"半自动闭环。
  - 优：零成本、零数据出域。
  - 劣：表格修复的主力缺失，试点指标（重建覆盖率）会接近零，失去了本次升级的主要价值。
- **裁决：A**（2026-09-06）——本期为 DeepSeek 单一实现；接口抽象与多模型接入**有需要时再做**（R8 已登记该延后项的触发条件）。无 key/超预算时仍按 FR-D7 自动降级为"诚实标记+跳过"。

### Q3　MD 与 HTML：主从关系还是双交付？【已裁决：B 修订——JSON 默认，MD/HTML 按需】

**术语**：MD（Markdown）是纯文本源格式，适合编辑、版本管理、喂给 RAG/大模型；复杂表以"内嵌 HTML `<table>`"表达。HTML 是渲染成品，浏览器直接打开，表格边框、合并单元格所见即所得。

- **选项 A：MD 主交付，HTML 派生**。
  - 优：单一出口，维护一处。
  - 劣：人读场景差——很多 Markdown 查看器不渲染内嵌 HTML 表格，打开就是一堆标签；也无法用样式保证表格边框可见（研究报告常见坑 #8：HTML 表默认无边框，易被误判为"转错了"）。
- **选项 B：双交付平级**——同一份 JSON 同时生成 MD（机读/编辑用）和自包含 HTML（人读用）。
  - 优：两个用途正交，各取所长；两者从同一 JSON 生成，边际成本很低；HTML 可自带溯源角标与表格样式，验收演示直观。
  - 劣：产物多一类文件；需保证两个序列化器读同一份数据（单一事实源约束）。
- **裁决：B 的修订版**（2026-09-06）——**JSON 是默认唯一交付格式；MD 与 HTML 的生成能力内置，但仅在用户明确要求时生成，无要求不主动生成**。能力上双通道平级（同一 JSON 派生，保证一致），触发上按需。

### Q4　图片抽取的默认范围：全类型 还是仅图集/扫描件？【已裁决：A】

**术语**："图片抽取"= 把 PDF 中的插图（照片、图表、节点大样）裁成独立 PNG 存入 assets/ 目录，JSON 里只留索引（路径+页码+坐标+图注）。数字版 PDF 可无损抽出内嵌原图；扫描件整页是一张大图，需用版面分析找出插图区域再裁。

- **选项 A：所有类型 PDF 默认开启**。
  - 优：三形态（文字/表格/图）完备一次到位；MD/HTML 能在原阅读位置还原插图；图集类约半数信息在图上，不开等于没解析（规范 v3.0 §0.2 的既有结论）。
  - 劣：处理时间与存储增加；有误裁风险（把表格误裁成图片 → 靠 FR-B5"图/表先分类再分流"压制；把项目符号裁成垃圾小图 → 靠面积/边长过滤阈值压制）。
- **选项 B：仅图集（atlas）和扫描件默认开启**。
  - 优：省资源，聚焦痛点最集中的文种。
  - 劣：条文规范里的少量插图（如构造示意）静默丢失，三形态不完备。
- **裁决：A**（2026-09-06）——全类型默认开启，小图过滤阈值在试点册上标定后写死默认值。

### Q5　本地重型引擎（PaddleOCR-VL / MinerU）是否实装？【已裁决：A】

**术语**：这两个是 2025–2026 年开源文档解析的 SOTA 模型（0.9B–1.2B 参数），能把整页 PDF 直接解析成带表格结构的 Markdown/JSON，表格 TEDS 最高 94.76——但为 GPU 优化。本机是无 GPU 单机 CPU。

- **选项 A：仅留接口文档，不实装**。
  - 优：不占工期；未来有了 GPU 机器，按接口即插即用。
  - 劣：本机无法用 SOTA 引擎。
- **选项 B：实装为可选执行器（CPU 模式）**。
  - 优：无 API 时多一条本地出路。
  - 劣：实测依据不利——MinerU pipeline 后端纯 CPU 模式 OmniDocBench 仅 86.47（vs 其 GPU+VLM 模式 95.69），且 VLM 在 CPU 上单页推理可达分钟级；安装依赖重（PaddlePaddle/vLLM 生态）；本期收益/工期比低。
- **裁决：A**（2026-09-06）——仅留接口文档。

### Q6　存量 v3 JSON 是否回填行级坐标？【已裁决：A】

**术语**："回填"= 用新版 OCR（保留每行 box 坐标）重跑老 PDF，把 `lines[]` 坐标层补进既有 JSON。没有坐标层，老文件的破表无法走"定位→裁剪→视觉修复"闭环，只能走高成本整页回退。

- **选项 A：随用随跑**——哪册要做表格修复，才重跑哪册的 OCR 回填坐标。
  - 优：不浪费机时；断点续跑+幂等使重跑本身廉价（每页落盘，中断不丢）。
  - 劣：首次修复某册时多一段 OCR 等待（CPU 约 2–11 秒/页）。
- **选项 B：一次性全量回填**。
  - 优：所有存量立刻获得完整坐标层。
  - 劣：为暂无修复需求的册子消耗机时；重跑期间占用机器。
- **裁决：A**（2026-09-06）——随用随跑。

### Q7　技能形态：就地升级 还是 新开 pdf-parse-v4？【已裁决：A】

**术语**："技能"= SKILL.md + 脚本资产的整体（触发词、流程、工具）。数据格式兼容性由 `schema_version` 治理，与技能叫什么名字是两回事。

- **选项 A：就地升级 pdf-parse-v3**（技能内容升级，数据 schema 升版）。
  - 优：用户既有调用习惯与触发词不变；不会出现两个相似技能抢触发词；维护单点。
  - 劣：技能内部变化大，需要更新 SKILL.md 与测试。
- **选项 B：新建 pdf-parse-v4 并存**。
  - 优：旧版完全冻结，零回归风险。
  - 劣：两个技能触发词高度重叠（"读 PDF/PDF 转 JSON"），路由歧义；双倍维护；旧技能不再演进形成僵尸资产。
- **裁决：A**（2026-09-06）——就地升级。

### Q8　HTML 的溯源呈现：角标 还是干净视图？【已裁决：A】

**术语**："溯源角标"= 在 HTML 的每个表/图/条文旁用小字标注其物理页码与质量状态（如 `P45 · fixed`），点击可回查。

- **选项 A：角标可开关，默认开**。
  - 优：A6 可溯源性从数据层延伸到阅读层——读者当场知道"这表数据可不可信、出自哪一页"；验收与抽检效率高。
  - 劣：视觉上有额外信息；打印场景可能嫌干扰（故需可关）。
- **选项 B：HTML 干净视图，溯源只留在 JSON**。
  - 优：页面干净，适合对外分发。
  - 劣：status=uncertain/unreadable 的表在人读界面失去警示，违背"诚实标记要能被看见"的设计初衷（FR-E6 的精神）。
- **裁决：A**（2026-09-06）——角标可开关、默认开。

### Q9　验收基线：先出数再定 还是 预先承诺？【已裁决：A】

**术语**："基线"= §9.1 指标的目标值（如"自动校验通过率 ≥ X%"）。

- **选项 A：试点册（GBJ16-87 第1册）跑完，用实测数据定基线**。
  - 优：目标值有据可依；与试点方案 §10 既定口径一致。
  - 劣：定稿时指标栏是"待定"，需试点后回填。
- **选项 B：现在预先承诺数字**。
  - 优：目标明确。
  - 劣：无先验数据支撑，承诺即拍脑袋；视觉重建在老扫描件上的表现无公开基准可参照。
- **裁决：A**（2026-09-06）——硬性指标（守恒 100%、标记完备 100%、溯源 100%）预先承诺；软性指标（重建覆盖率、校验通过率）试点出数后定基线。

### Q10　是否批准中文友好视觉/文档解析 API 的对拍测试？【已裁决：A】

**术语**："对拍测试"= 用同一批真实样本同时调用多个候选 API，按统一指标横向比较。"主解析器"= 文档解析的第一执行通道（此前是本地 OCR，候选是云端专用模型 API）。

- **裁决：A**（2026-09-06）——批准以智谱 GLM-OCR 与阿里 Qwen3-VL-Flash 两路对拍。随后完成 4 页难例对拍与 180 页整册补测（用户选 B 增补），产出《视觉与文档解析API对拍测试报告》v1.1。

### Q11　主路线是否切换为 GLM-OCR 整页解析为主？【已裁决：A+】

**术语**："主路线切换"= 扫描件的默认解析通道从"本地 OCR + 视觉模型逐表兜底"改为"GLM-OCR 云端整页一次解析 + 本地校验门 + 缺陷阶梯"。"校验门"= 对每张表自动执行的三信号检查（结构守恒、缺陷签名、交叉对位），任一命中即进入修复阶梯。"交叉对位通道"= 本地 RapidOCR 的行级识别结果与 GLM 表格数值按行对位核验——它是发现"无横线子行错位"（D3 类，错位后网格仍守恒、守恒检查抓不住）的独立观测手段。"缺陷阶梯"= 规则修复 → 裁剪重译 → 第二意见复核 → 诚实标记，逐级升级、不覆盖原文。

- **选项 A：切换**——本地 OCR 转可选增强。
- **选项 A+：切换，且交叉对位通道默认开启**——每册多几分钟免费本地计算，换 D3 类缺陷的独立观测信号。
- **选项 C：不切换**——GLM-OCR 仅作兜底器平替。
- **裁决：A+**（2026-09-06）。依据：整册补测 100% 成功率、表格零漏检、86.3% 守恒直通、¥0.1615/册；缺陷全部可观测可控（《缺陷处理与主路线融合架构思考》§1–§3）；本地组件集体转任校验与兜底角色，多样性冗余保留（§5.2）。

### Q12　主路线切换的配套默认规则【待确认，已给建议默认】

1. **出域默认规则**：默认允许文档出域（扫描件经 GLM-OCR 解析）；用户声明敏感的文档经 `--no-egress` 参数或配置项强制走纯本地路径（功能降级为本地管线 + 诚实标记）。*建议默认：通过。*（术语："出域"= 文档内容离开本机发送到云端 API。）
