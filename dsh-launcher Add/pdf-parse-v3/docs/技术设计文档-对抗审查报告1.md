## 0. 结论摘要

- **总体判定**：设计文档的**骨架是成立的、可交付进入详细设计**，无阻断级（blocking）问题；但存在 **8 项严重（major）**、若干轻微与建议级缺陷，须在详细设计前闭合。
- **第一性原理层面**：三形态（文字/表格/图）拆解、「中间表示表达力 ≥ 源结构复杂度」「忠实优先于结构」三条推论正确且贯穿全文，是本设计的真正优点。
- **控制论层面**：把链路建模为「被控对象 = 信息保真度」的反馈系统、并以「执行通道单一、观测与纠偏通道冗余独立」为结构原则，方向正确；但**观测通道的冗余性与独立性被过度宣称**——最危险的 D3 缺陷只有一个传感器，且「GLM 与 RapidOCR 误差不相关」这一独立性假设从未被验证（详见 M3/M4）。
- **最需警惕的共性问题**：若干「硬性」验收指标（漏检率 0、缺陷台账捕捉率 100%）在定义上**不可证伪/不可测量**，会削弱「无人复核、用指标说话」这一验收前提的可靠性（M5）。
- **交叉引用**：FR/Q/R/V 编号与《需求确定书》一致；实测数字（¥0.1615 / 86.3% / 73 表 / 180/180 / 4.25s）与《对拍测试报告》一致；但存在版本号自相矛盾（标题 v0.1 vs 字段 v0.3）等轻微问题。

> 通过判据说明：本报告为仅报告模式，不冻结通过判据；严重级清单供后续修复闭环或用户裁决使用。

## 1. 分级意见单（按严重度排序）

### 1.1 严重级（major，8 项）

#### M1 — 「结构守恒直通率 ≥85%」的目标值与基线口径错位，且 MS-2 出口判据自相矛盾

- **anchor**：§7.1 指标表「结构守恒直通率」（行 232）＋ §7.2（行 241）＋ §8-2「黄金夹具」（行 536）＋ 里程碑 MS-2 出口判据（行 558）；对照《对拍报告》§8.2。
- **basis**：86.3%（63/73）是 **GLM 原始 HTML 输出**直接过守恒门的比例（《对拍报告》§8.2「63/73 全过」）。而 §7.1 把「结构守恒直通率」定义为「无需修复即过守恒门的表占比」，该指标在**适配层（M6 幻影列坍缩 / 占位空 td 丢弃）之后、缺陷阶梯之前**测量。两者不在同一管线位置：幻影列坍缩恰恰会把 10 张守恒失败表（D2 类 rowspan 过声明）**改判**，使后适配层通过率必然 ≠ 86.3%。故「以 86.3% 作 ≥85% 的基线」是把原始模型指标与系统级指标混为一谈；同时 MS-2 出口判据「守恒判定与实测基线一致」与「幻影列坍缩改变守恒结果」在定义上互相冲突——坍缩若生效，判定就不可能「与基线一致」。
- **confidence**：high。
- **type**：一致性 / 口径。
- **suggestion**：明确「直通率」的测量点（建议固定为「适配层输出、缺陷阶梯介入前」），并用黄金夹具在**同一测量点**重跑 73 表得到新基线后，再定目标值；MS-2 判据改为「坍缩后的守恒结果与『坍缩应修复的 D2 子集』一一对应」，而非「与 86.3% 一致」。

#### M2 — 「出域只发生在 M4 一处」与第二意见（DeepSeek/Qwen）出域未收敛

- **anchor**：§4「出域只发生在 M4 一处」（行 482）＋ §3.1 M4 契约（行 419–428，仅 `glm_parse_page`/`glm_reparse_crop`）＋ §10「第二意见复核 DeepSeek/Qwen」（行 286）＋ §5 资产映射「shootout.py → M4（GLM/Qwen/DeepSeek 客户端基座）」（行 497）。
- **basis**：三处陈述互相矛盾：① M4 名为 `glm_client.py` 且契约只有 GLM 函数；② §10 把 DeepSeek/Qwen 列为独立角色；③ §5 又把 shootout.py 的三厂商客户端基座全部映射给 M4。若 M4 确为唯一出域点，则第二意见的「窄任务 prompt + strict schema」接口（FR-D4 要求）在 §3.1 契约中**缺失**，且 `--no-egress`「短路 M4」能否同时阻断 DeepSeek/Qwen 出域**未被证明**——这直接关系到 §8/Q12「敏感文档强制本地」这一强制约束能否成立。
- **confidence**：high。
- **type**：一致性 / 合规性（出域）。
- **suggestion**：要么把 M4 明确定位为「多厂商视觉客户端」并改名、在 §3.1 补出第二意见窄任务接口，并显式声明 `--no-egress` 阻断**全部三厂商**；要么为第二意见新增独立客户端模块并修订「唯一出域点」表述。二者取一，且须在详细设计前写死。

#### M3 — D3（无横线子行错位，最危险缺陷）只有单一传感器，违反「观测通道冗余」原则

- **anchor**：§2.2 控制论结构表「观测与纠偏通道必须冗余且相互独立」（行 59）对照 KD4「交叉对位为 D3 唯一观测信号」（行 509）；另见《架构思考》§1-D3（行 37）称 D3 为「最危险的一类」。
- **basis**：§2.2 立下「观测通道必须冗余」的总原则，但设计自己承认（KD4）D3 只能被「交叉对位」这一个信号捕获——守恒门抓不住（错位后仍守恒），缺陷签名只覆盖 D1/D2。于是**风险最高的缺陷类反而落在唯一的、且最不可靠的传感器上**（本地 OCR 行对位，见 M4），与总原则直接冲突。
- **confidence**：high。
- **type**：逻辑 / 边界。
- **suggestion**：为 D3 补一个独立观测通道（例如几何行/列聚类对子行错位的判定，或第二意见的窄任务「逐行序号-数值」转写作为低频兜底），并明确 D3 在无第二传感器时的降级口径（如实标记为 uncertain 而非自信放行）。

#### M4 — 「GLM 与本地 OCR 误差不相关」的独立性假设未被验证

- **anchor**：§2.2「必要多样性：误差模式互不相关的双通道互为校验」（行 69）；《架构思考》行 85「它的错误与 GLM 的错误不相关」。
- **basis**：整套安全态（诚实标记）依赖交叉对位这一「独立观测」成立；但独立性在此是**断言而非实测**。GLM-OCR 与 RapidOCR 同为对同一张扫描图做 OCR 的深度学习模型，在低 DPI、模糊、字形相似（如 0/6、1/7）等退化输入上**可能系统性共错**；若两通道在错误上正相关，交叉对位会给出「假一致」的虚假确认，反而降低安全态的可信度。《对拍报告》§2 已明示 RapidOCR「本身有错漏」，却从未分析两模型错误是否相关。
- **confidence**：medium（独立性是否成立需实测，方向性风险成立）。
- **type**：逻辑 / 边界。
- **suggestion**：利用既有对拍样本（GLM 与 RapidOCR 已同时跑过同一批页），做一次「两通道不一致率 / 共错率」实证，量化交叉对位的真实灵敏度；若共错率不可忽略，须把交叉对位降级为「提示信号」而非「放行依据」。

#### M5 — 「表格漏检率 0」与「缺陷台账捕捉率 100%」两项硬指标不可证伪

- **anchor**：§7.1 指标表「表格漏检率」（行 231）与「缺陷台账捕捉率」（行 227）；对照《对拍报告》§8.2 的漏检口径。
- **basis**：①「漏检率 0」的实测依据是「OCR 文本含『表N』但 GLM 未检表的 25 页均确认是引用」——即漏检只对**有『表N』文字信号**的表可测；凡无题号、题号被 OCR 读错、或纯图无文字的表一旦漏检，该指标无从发现，故「0」是仅在该口径下的上界，不能外推为绝对 0。②「捕捉率 100%（缺陷均被登记、无静默通过）」在逻辑上**不可验证**：被静默漏掉的缺陷正是传感器看不见的，指标本身无法计数。两项「硬性 100%」要么平凡成立、要么不可证伪，与「无人复核、用指标说话」的验收前提形成张力。
- **confidence**：high。
- **type**：逻辑 / 合规性（对外承诺数据）。
- **suggestion**：把两项改为「可测口径下的上限/抽样复核」表述——漏检率改为「基于『表N』信号与人工抽检的真值子集的漏检率」，捕捉率改为「对已知缺陷签名集（D1/D2/D3）的捕捉率」；保留「100%」但显式限定口径，并在交付说明中声明指标的可测边界。

#### M6 — FR-C2（线框表几何重建，P1）与 FR-C4（无框表，P1）无归属模块，且已有原型（研究报告附录A）未被纳入资产映射

- **anchor**：§2 模块分解表 M1–M13 的「对应需求」列（行 399–413）对照需求 FR-C2/FR-C4（行 150/152）；§5 资产映射（行 486–500）未见「几何表格重建」原型来源。
- **basis**：逐行核对模块表：M3 只认领 FR-C3（pdfplumber 确定性提取），M6 只认领 HTML→网格（FR-C1/C5/C6），M7 只认领校验门（E 组），M8 认领 D 组。**FR-C2（形态学线段检测→网格聚类→合并推断，验收「合成复杂表 100% 还原」）与 FR-C4（无框表 x/y 聚类）没有任何模块认领**。而《研究报告》附录A 正是 FR-C2 的完整算法原型（线段检测/网格聚类/合并推断/词块归格），§5 资产映射却只把「研究报告 §5」指给 M10 的图件检测，遗漏了附录A 这一可直接提炼的表格几何重建原型。P1 级需求既无归属又错失现成资产。
- **confidence**：high。
- **type**：完整性。
- **suggestion**：明确 FR-C2/C4 的归属（建议并入 M6 作为「GLM 之外的几何重建子模块」，或并入 M7/M8 作离线校验与兜底），并在 §5 资产映射中补「研究报告附录A → 表格几何重建模块」的提炼条目。

#### M7 — 分诊为「页级」路由，无法处理「页内混合」（文字层页中嵌入栅格表格区域）

- **anchor**：§4 系统路线「混合 → 按页走两路之一」（行 109）＋ FR-A1 分诊粒度（行 130）＋ §8 边界清单（行 258）。
- **basis**：分诊把每页归入 text / scanned / hybrid 之一，混合仅指「页级混合」并按页二选一。但真实 PDF 常见**单页内**既有文字层又有扫描嵌入的表格图片：此时 PyMuPDF 文字层路径对栅格表不可见（无文字可提取），整页走文字层会**静默丢失该表格**。§8 边界清单列了「伪文本层」「双栏串行」等，却未列「页内图文混合/文字层页含栅格表」这一高频形态；试点册为纯扫描册，该形态未被实测覆盖，故该缺口是「未暴露」而非「不存在」。
- **confidence**：high。
- **type**：边界。
- **suggestion**：在分诊增加「页内区域级探测」（文字层覆盖率 + 页内图像块/线框检测），对疑似页内栅格表区域追加 GLM 裁剪解析或几何重建；并把「页内混合」补入 §8 边界显式处理清单。

#### M8 — 第二意见（DeepSeek）通道无预算上限，且「单册 ¥1」的预算范围语义含糊

- **anchor**：§8「单册 GLM 预算上限 ¥1」（行 254）＋ FR-D5「DeepSeek 通道峰谷时段提示」（行 166）＋ §4 参数集中「预算上限（单册 ¥1）」（行 482）＋ M12「预算闸（¥1/册）」（行 412）。
- **basis**：¥1 封顶被反复限定为「GLM」或「¥1/册」语义不一；而第二意见通道用 DeepSeek（输入高峰 ¥3.0/M、输出 ¥9.0/M，约为 GLM 单价的 15–45 倍）**只有「峰谷提示」、无封顶**。缺陷阶梯对缺陷表可触发裁剪重译 + 第二意见，DeepSeek 峰值价下即便少量表也可能显著超出 GLM 主通道成本，使「成本可预算」这一系统目标在第二意见路径上落空。FR-D8 的「一次定向重试」虽有限制，但未覆盖「第二意见调用总量」这一预算维度。
- **confidence**：high。
- **type**：边界 / 合规性（成本）。
- **suggestion**：为第二意见通道设独立预算闸（可与 GLM 合并为「单册视觉总预算」并显式分解主/复核两部分），并把 DeepSeek 的峰谷价差从「提示」升级为「可配置的封顶 + 超限降级」。

## 3. 正面确认项（实事求是，非恭维）

以下为该设计**经核对成立**、且构成其真实价值的要点：
