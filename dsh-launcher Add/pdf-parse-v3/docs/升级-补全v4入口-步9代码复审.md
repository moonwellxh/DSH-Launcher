### 建议

**[建议-1] mock 带默认值且不校验转发 → 单测无法捕获 N9 型缺参回归（守护力缺口）**
- **anchor**：test_ms3_ladder.py L66-74（`page=None, doc_sha1=None, render_reg=None` 默认）＋L86-88（run_ladder ctx 无 page/doc_sha1/render_reg 键）。
- **basis**：N9 缺陷恰是「second_opinion 未传 3 个必填 kw-only」；mock 带默认值等价于把必填放宽为可选——若 ladder 再次漏传，此套测试仍全绿（R1-R6 走 CROP/SECOND 分支的用例均无法分辨转发缺失）。生产签名（vision_client L661/L669）无默认，mock 与生产契约不一致。
- **confidence**：高。
- **建议处置**：mock 改为无默认（与生产同形）或记录收参并与 ctx 期望值断言（一行断言即可把「转发正确」钉成回归用例）。

**[建议-2] --pages/_parse_pages 无任何单测；无效规格（如 "abc"）静默产出空 v4 且 exit 0**
- **anchor**：orchestrator.py L295-314（无效片段被 continue 吞掉，返回空 set）＋L323/L332-333（空 set → tri["pages"]=[] → OK pages=0 空产物）。
- **basis**：tests/v4 全目录 grep 无 `--pages`/`_parse_pages` 用例；无效页规格的失败模式是「exit 0 + 空 v4」，用户无感知会误判成功。argparse help 明示用途为「大文件前 N 页验收」，属新功能面，应有单元与无效输入报错。
- **confidence**：高。

**[建议-3] ctx.page 取值口径不一致：CROP 有兜底、SECOND/resolve_hint 无兜底**
- **anchor**：defect_ladder.py L206（`ctx.get("page", ctx.get("page_number", 1))`）vs L229/L274（仅 `ctx.get("page")`，缺键即 None）。
- **basis**：当前唯一 ctx 构造方（pipeline.py L72）恒设 `page=page_no` 为 int，无即时风险；但未来任何只带 `page_number` 的 ctx 会让 CROP 走 page、SECOND 走 None，指纹与页语义分裂。建议统一为同一取值式或把 page 声明为 ctx 必需键（与 doc_sha1/render_reg 的兜底风格并列）。
- **confidence**：高（当前影响面=0，仅协议健壮性）。

**[建议-4] 冻结升级设计 §3.2 的 process_page_md 调用清单滞后于实物增量**
- **anchor**：`docs/升级-补全v4入口-详细技术设计.md` §3.2 L286-288（示例调用仅 ocr_lines/ocr_available/m4/raw_resp）↔ 实物 orchestrator.py L274-281（另传 png/doc_sha1/render_reg）＋pipeline.py L53-54（新参）。
- **basis**：设计为冻结件、修复为 N9 真跑后增量，实物是设计的超集（额外传 3 个 kw），功能无害；但文档-实物一致性（本升级 R-06 口径）在此处未同步，后续复跑/维护易误删增量参数。
