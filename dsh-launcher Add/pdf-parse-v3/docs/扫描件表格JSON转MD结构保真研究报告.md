# 图片型PDF表格与图片 → JSON → Markdown 结构保真研究报告

**日期**：2026-09-05　**方法**：第一性原理分析 + 端到端实验复现 + 主流工具链核查

---

## 摘要（结论先行）

问题**两个环节都有，但性质完全不同**，不能笼统归因：

**PDF→JSON 是"信息重建"问题**。图片型PDF里根本没有"表格"这个对象，只有一堆字符像素和线条。表格结构（几行几列、哪些单元格合并）必须由机器从几何关系重新推断出来。如果你的JSON里只有按阅读顺序排列的文本行（或没有坐标、没有rowspan/colspan的扁平单元格列表），那么结构信息在这一步就已经**永久丢失**了——后面无论怎么转MD都救不回来，垃圾进垃圾出。

**JSON→MD 是"表达能力"问题**。标准Markdown（GFM）管道表格在设计上就只能表达"m×n简单网格+单行表头"，**语法层面不存在**合并单元格、多级表头、单元格内换行、嵌套表格的表达方式。所以即使JSON里结构完好，只要朴素地拼成 `| a | b |` 管道表，复杂表格必然变形。这是Markdown格式的表达力上限，不是代码bug。

**解决办法一句话**：PDF→JSON阶段用带"表格结构识别（TSR）"的引擎产出**含合并信息的网格JSON**；JSON→MD阶段按表格复杂度分级序列化——简单表用管道表，复杂表**在MD中内嵌HTML `<table>`**（Markdown原生支持块级HTML，GitHub/Typora/VS Code等主流渲染器都能正确渲染）。本报告用实验完整验证了该方案：结构100%保真。

**对纯图片（非表格）内容**，同样可行且更直接：把图片区域裁切成独立文件入库，JSON中建立与文本块平级、锚定阅读顺序的图片索引，MD中用 `![]()` 在原位引用——日后取用、检索、还原显示都走这个索引。方案与实验见第五节。一、第一性原理拆解：表格到底是什么

### 1.1 表格的逻辑本质

剥离一切表象，一张表格的逻辑模型只有四个要素：

1. **网格**：n行 × m列的二维坐标系；
2. **单元格内容**：每个格子里的文本（可能多行）；
3. **合并关系**：某些逻辑单元格横跨多个网格位置（rowspan/colspan），被覆盖的位置不再独立存在；
4. **阅读顺序与语义角色**：哪些是表头（th）、哪些是数据（td）、表与表之间的层级。

只要能无歧义地记录这四个要素，表格就**可以被无损地序列化和重建**。这是判断一切中间格式"够不够用"的标尺。

### 1.2 三个环节各自的信息模型

| 环节 | 实际承载的内容 | 对表格四要素的表达能力 |
| --- | --- | --- |
| 图片型PDF/扫描图像 | 像素点阵。文字是字形，线是矢量或墨迹，**没有任何表格语义** | 零。结构必须靠推断重建 |
| OCR纯文本JSON | 文本行 + （也许有）阅读顺序 | 只承载了"内容"，网格/合并/角色全丢 |
| **结构保真JSON**（网格模型） | 行列数 + 每格`rowspan/colspan/text/bbox` | **完备**，与HTML表格表达力等价 |
| GFM管道表（`\\| a \\| b \\|`） | m×n简单网格、一行表头、格内纯文本单行 | 真子集：无合并、无多级表头、无格内换行 |
| MD内嵌HTML `<table>` | 完整HTML表格模型 | **完备**（rowspan/colspan/th/`<br>`均支持） |

### 1.3 关键推论（信息论视角）

每一次格式转换都是一个映射。若**目标格式的可表达空间是源格式的真子集**，则映射必然多对一，信息必有损，且损失不可逆——下游任何聪明的后处理都无法区分"原本就长这样"和"被压扁成这样"。

由此得到**无损链路的充要条件**：

1. 中间表示的表达力 ≥ 源文档的表格结构复杂度；
2. 每个转换器在该表达力范围内做保真映射（不多丢、不乱猜）。

你的现状是：第一步把表格压成了"行文本JSON"（表达力不足，丢网格与合并），第二步又把信息排进GFM管道表（表达力再次不足）。**两次压缩叠加，表格就"乱了"**。病是两处都有的，要分段治。

### 1.4 两个环节的故障模式对照

|  | PDF → JSON | JSON → MD |
| --- | --- | --- |
| 问题性质 | 重建/推断问题（从像素猜结构） | 序列化/表达问题（结构塞不进语法） |
| 典型故障 | 只输出文本行；无线框表完全丢失行列；合并单元格被拆成碎片；跨页表被腰斩 | 管道表错列；合并表头被拉平成行；格内换行把一行炸成多行；`\\|`字符截断单元格 |
| 可否做到近无损 | 可以（TSR模型/几何重建，工业界已成熟） | 对复杂表**不可能用纯GFM做到**，必须引入HTML或改变产出形态 |
| 责任判定速查 | 打开JSON搜`rowspan`/`colspan`/`bbox`/行列坐标——**没有就是这儿断的** | JSON里结构齐全但MD里没有——**就是这儿断的** |

## 二、实验复现：把"乱了"三个字变成可观测的事实

### 2.1 实验设计

合成一张典型的中文复杂表格扫描图（故意叠加噪声模拟扫描件），它一次性集齐四类"杀手"结构：**纵向合并**（"项目"跨2行）、**表头横向合并**（"2024年度/2025年度"各跨3列）、**数据区横向合并**（"（并购后口径）"跨2列）、**整行合并+格内换行**（末尾注释行跨7列、两行文字）。

然后跑两条链路对比：

- **链路A（朴素，复现问题）**：Tesseract OCR → 按行拼文本的JSON → 每行按空格切列、拼成GFM管道表；
- **链路B（结构感知，验证方案）**：形态学线段检测重建网格 → "缺失的线段=合并"推断rowspan/colspan → 词块按坐标归格（被覆盖格的词路由回合并锚点）→ 网格JSON → MD内嵌HTML表格。

### 2.2 链路A的中间产物与结果

OCR后朴素JSON（这就是大量自研脚本和部分轻量工具的真实产出形态）：

```json
{"lines": [
  {"text": "2024 年 度 2025 年 度"},
  {"text": "收入 成 本 毛利 收入 成 本 毛利"},
  {"text": "东 大 区 120.5 80.3 40.2 135.0 88.1 46.9"},
  {"text": "华南 大 又 并 购 证 210.8 150.2 60.6"},
  {"text": "并 购 了 公司 ， 经 审计"} ]}
```

朴素转MD后（节选）：表头行只有6个词、数据行9个词，渲染器一律按左对齐补齐——`135.0`被顶到"80.3"的列下，"华南"行因合并单元格缺词而整体错位，注释行被炸成一行假数据。**数字与列名的对应关系被静默改写**，这是最危险的：不是"难看"，是"读错"。

### 2.3 链路B的中间产物与结果

结构保真JSON（网格模型，节选）：

```json
{"n_rows": 7, "n_cols": 7, "cells": [
  {"row":0,"col":0,"rowspan":2,"colspan":1,"text":"项目"},
  {"row":0,"col":1,"rowspan":1,"colspan":3,"text":"2024年度"},
  {"row":0,"col":4,"rowspan":1,"colspan":3,"text":"2025年度"},
  {"row":4,"col":1,"rowspan":1,"colspan":2,"text":"(并购后口径)"},
  {"row":6,"col":0,"rowspan":1,"colspan":7,"text":"注:2025年含新并购子公司，数据未经审计<br>(口径详见附注三)"} ]}
```

由它生成的MD（内嵌HTML）经浏览器渲染，与原扫描图逐项核对：**5处合并全部正确还原，7×7网格完全吻合，28个逻辑单元格内容除"项目"被OCR漏识一字外全部正确**（文字精度是OCR引擎的问题，与结构保真是两个正交的轴，换PaddleOCR/商用引擎即可补齐）。

## 三、问题定位：三分钟自查你的链路断在哪

1. **打开你的JSON文件**（不是MD），查找`rowspan`、`colspan`、`cells`、`bbox`、行列坐标字段：

- 都没有，只有按行的`text` → **病根在PDF→JSON**。结构已永久丢失，换再好的MD生成器也没用，回到第四节L1重做；
- 有坐标但只有词级别、无单元格/网格 → 半成品，需要补一层"几何网格重建"（附录代码可直接用）；
- 有完整网格与合并信息 → 病根在JSON→MD，跳到第四节L2。

2. **检查MD里的转义**：如果单元格内容本身含`|`，朴素拼接会把它切成两列——搜索替换为`\|`；格内换行替换为`<br>`。这两处是"看着简单却总翻车"的高发点。
3. **抽样对数**：随机挑3个跨列合并下方的数字，人工核对其列归属。错位即结构断，不错位只是难看即纯渲染问题。

## 四、解决方案（分层实施）

### L1　PDF→JSON：让JSON承载完整表格结构

原则：**把"表格结构识别"当作一等公民，而不是OCR的副产品**。三条路线按资源选自：

- **直接用成熟解析引擎（推荐）**：以下引擎均原生输出带合并信息的表格（HTML或等价网格JSON），并已处理扫描件OCR——
- **MinerU（OpenDataLab/上海AI Lab）**：表格→HTML，VLM+OCR双引擎，支持扫描件、109种语言、跨页表合并；
- **PaddleOCR PP-StructureV3**：内置PP-TableMagic（单元格检测+结构识别），直接输出HTML结构；
- **IBM Docling**：TableFormer模型，开`do_table_structure=True`+`do_cell_matching=True`+`TableFormerMode.ACCURATE`，复杂表头表现好；
- **商用API**：Azure Document Intelligence、AWS Textract（TABLES特性）、Mathpix，省心但有成本与数据出域问题。
- **自研几何重建（线框表有效，附录有完整代码）**：形态学提取横/竖线段 → 聚类成网格线 → **逐段检查网格线是否存在，缺失即合并** → OCR词块按中心点归格、被覆盖格路由回锚点 → 网格JSON。本报告实验即此路线，7×7含5处合并全部还原。
- **无线框表（三线表等）**：线段检测失效，改用文本块x坐标聚类推断列、y聚类推断行，或用学习型TSR模型（TableFormer/PP-TableMagic直接出结构）。这类表建议直接交给上述引擎。

**输出规范**（自定义JSON时照此建模，与Docling/Azure的网格模型对齐，下游工具链通用）：

```json
{"tables":[{"n_rows":7,"n_cols":7,"cells":[
  {"row":0,"col":0,"rowspan":2,"colspan":1,"text":"项目","bbox":[x0,y0,x1,y1],"is_header":true}]}]}
```

### L2　JSON→MD：按复杂度分级序列化

先对每张表计算复杂度：存在任何`rowspan>1`或`colspan>1`、多级表头、格内多行 → 判为**复杂表**。

1. **简单表 → GFM管道表**，并强制转义纪律：内容中`|`→`\|`；换行→`<br>`；表头不足/多余时按网格补齐或裁剪，绝不按词数对齐。
2. **复杂表 → MD内嵌HTML `<table>`**（本报告验证的方案）：`<th rowspan colspan>`/`<td>`直译网格JSON，格内换行用`<br>`。CommonMark与GFM规范均允许块级HTML，GitHub、Typora、VS Code、Obsidian均正常渲染。这正是MinerU等工业级工具的共同选择——表格在MD里以HTML呈现。
3. **极端复杂表（嵌套表、超大跨页表）→ 降级策略**：拆成多张简单表+小标题；或裁原图嵌入`![表格](path)`，图下附OCR文本供检索——保真优先于可机读。
4. **可选妥协形态**：若下游是必须吃纯管道表的工具（某些RAG切分器），则把合并单元格**显式展开**（被覆盖格重复填充锚点内容或留空并加列名前缀如`2024年度_收入`），用"信息冗余"换"列对齐正确"——宁可冗余，不可错列。

### L3　质量校验闭环（防止"静默读错"）

1. **守恒检查**：`Σ(rowspan×colspan) == n_rows × n_cols`，不等即结构自相矛盾；
2. **渲染diff**：MD→HTML渲染截图，与原图并排目检（本报告对比图即此法的产物）；
3. **关键值抽检**：金额、合计行做横向/纵向加总验证；
4. 有标注条件时用**TEDS**（树编辑距离相似度）对结构与文本一并打分，这是表格识别领域的标准指标。

## 五、纯图片（非表格）的抽取与索引

文档中的插图（照片、图表、流程图）没有结构重建问题——它本身就是信息完备的位图——因此处理思路与表格相反：**不解析内容，整体切出、文件化入库、JSON只存索引**。这一节同样经端到端实验验证。

### 5.1 取图的两条路径（按PDF类型选）

- **数字PDF（非扫描件）**：优先**直接抽取内嵌原图**——PyMuPDF的`page.get_images()`或命令行`pdfimages`可将嵌入位图原样取出，无损且保留原始分辨率，优于页面重渲染截图。注意：矢量图（大量图表是绘图指令绘制而非位图）无法抽取，需用`page.get_pixmap(clip=rect)`按区域重渲染成位图。
- **图片型PDF/扫描件**：整页就是一张大图，没有内嵌图可抽，必须做**版面分析**定位图片区域再裁切。轻量做法是几何法——二值化后大核膨胀把致密图片区域并成一个连通域，按面积与致密度过滤掉细长的文本行（本报告实验即用此法，成功定位并裁出940×447的插图）；生产环境建议用版面分析模型（PP-StructureV3/Docling的布局模型），它同时完成figure/table/text分类，**避免把表格误裁成图片**而使第四节的工作作废。

### 5.2 JSON索引设计（决定日后取用与还原的质量）

核心原则：图片必须作为**与文本平级的block锚定在阅读顺序中**，而不是单独一个`images`数组——否则还原显示时无法知道它属于哪段文字之后。推荐schema（实验实证可用）：

```json
{"type":"image","id":"img_p1_1","page":1,
 "path":"assets/img_p1_1.png",
 "bbox":[183,173,1123,620],
 "hash":"fac2759de6dd",
 "caption":"图1  2025年季度收入分布",
 "alt":"柱状图：Q1-Q4季度收入，Q4最高"}
```

| 字段 | 作用 |
| --- | --- |
| `id`/`path` | 唯一标识+相对路径，assets目录随文档包迁移 |
| `page`+`bbox` | 页内坐标：可回溯原页核对，可用更高DPI重新裁切 |
| `hash` | 去重键：页眉logo、水印等重复图全库只存一份 |
| `caption` | 邻近图注关联（图注通常在图下方紧邻处，正则匹配`图\s*\d+`） |
| `alt`/`ocr_text` | 对裁出的图再跑一次OCR存入，图片内容即可被全文检索 |

### 5.3 MD还原显示

在原始阅读位置插入`![caption](path)`，图注以斜体紧随其后；需控制显示尺寸时改用`<img src="..." width="600">`。渲染器从相对路径取图，用户看到的就是原位置的插图。

### 5.4 实验验证

![图片检测、裁切与索引示意](图片抽取与索引示意.png)

实验页含标题、两段正文与一张柱状图插图（叠加噪声模拟扫描）。几何法检测以0.93致密度定位图片区域，裁切、建索引、生成MD全链路一次通过。注意图中图注被并入裁切范围（膨胀合并所致）——生产上应将图注作为文本单独关联进`caption`字段，并视需要决定是否从裁切图中剔除。

### 5.5 图片链路的特有坑

1. 裁切分辨率：扫描页渲染DPI至少200~300，否则裁出的图发虚；
2. 小图过滤：设面积/边长阈值，否则项目符号、装饰图标全变成垃圾图片；
3. 倾斜扫描件先deskew，否则bbox歪斜、裁进邻栏文字；
4. 不要用base64把图片内联进JSON（体积膨胀约33%且不可复用），文件+路径索引是正解；
5. 图与表先分类再分流：表格走第四节结构重建，图片走本节整体裁切。

## 六、常见坑清单

1. 把"表格识别"默认成"OCR"，JSON只有文本行——结构永久丢失的最大根源；
2. 朴素拼接管道表不转义`|`，一个竖线字符炸开整行；
3. 格内换行直接保留`\n`，一行变两行、列数对不上；
4. 按"词数"对齐列——合并单元格导致各行词数不同，必然错列；
5. 中文等宽错觉：源码里管道表对不齐只是难看，渲染层不受影响——别为它浪费时间，要修的是结构不是空格；
6. 跨页表格不做合并，一张表变两张；
7. 扫描件倾斜未矫正（deskew），线段检测和坐标聚类集体漂移——先做图像矫正；
8. 用渲染器是否显示边框来判断MD对错——HTML表格默认无边框，加`border`或CSS即可，与数据正确性无关。

## 附录A　核心算法（结构感知链路，实验实证可用）

```python
# 1) 线段检测：形态学开运算分离横线/竖线
bininv = cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY_INV+cv2.THRESH_OTSU)[1]
hz = cv2.morphologyEx(bininv, cv2.MORPH_OPEN, cv2.getStructuringElement(cv2.MORPH_RECT,(80,1)))
vt = cv2.morphologyEx(bininv, cv2.MORPH_OPEN, cv2.getStructuringElement(cv2.MORPH_RECT,(1,80)))

# 2) 线段聚类成网格坐标 grid_x / grid_y（容差8px）

# 3) 合并推断：网格线在每个单元格区间上"逐段存在性"检查
#    第r行底边在第c列区间无线 → (r,c)与(r+1,c)纵向合并（rowspan++）
#    第c列右边在第r行区间无线 → (r,c)与(r,c+1)横向合并（colspan++）

# 4) 词块归格：OCR词中心点定位(行,列)；命中被覆盖格时路由回合并锚点

# 5) 序列化：全部1×1 → GFM管道表（转义 | 和换行）；否则 → <table> HTML嵌入MD
```

图片区域检测（第五节实验用，几何法）：

```python
bininv  = cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY_INV+cv2.THRESH_OTSU)[1]
merged  = cv2.dilate(bininv, cv2.getStructuringElement(cv2.MORPH_RECT,(25,25)))  # 致密图区并成整块
for c in cv2.findContours(merged, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)[0]:
    x,y,w,h = cv2.boundingRect(c); solid = cv2.contourArea(c)/(w*h)
    if w*h > 40000 and solid > 0.35:   # 大块且致密=图片；细长条=文本行，滤掉
        crop = src[y-5:y+h+5, x-5:x+w+5]  # 从无噪原图裁切，留5px余量
```
