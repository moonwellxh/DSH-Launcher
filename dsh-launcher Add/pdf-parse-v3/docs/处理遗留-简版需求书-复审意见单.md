### 轻微-1　R-01（原轻微-1，第 2 次未闭合）「Windows subprocess+stdin 管道模拟 TTY 交互」字面不成立，Windows 单机仍无可执行路径，空转风险未根除

- **anchor**：对象 L39（§2.1 bullet 1「R-01 用 subprocess+stdin 管道模拟交互，或用 WSL/ConPTY」）、L83（§5 R-01「Windows Python 无 pty → 用 subprocess + stdin 管道模拟 TTY 交互（或声明 POSIX/WSL/ConPTY 环境）…选 C/B → exit2/1、留痕、无 v4 产物；测试卫生（finally 还原 stdin/isatty）…禁止空转 skip」）、L101（§6.2「Windows=subprocess+stdin 管道模拟」）；实物 `assets/v4/orchestrator.py` L147-188/L471-473；`tests/v4/test_orchestrator_pdf.py` L139-141。
- **basis**：①门控事实：TTY 分支由 `tty=sys.stdin.isatty()` 决定（orchestrator L471-473），交互 input() 仅在 isatty True 时可达（L161-188），非 TTY 直接中止 exit3（L156-160）；②管道≠TTY：subprocess 以 stdin=PIPE 启动的子进程，其 `sys.stdin.isatty()` 恒为 False（管道不是终端，Windows 与 POSIX 皆然）——测试文件自身 L139-140 已自认「subprocess 下 isatty False → 需用 pty 才为 True」。故「subprocess + stdin 管道喂 '2\n'/'3\n'」只能走非 TTY 分支 exit3，**选 C/B → exit2/1 的断言在字面主路径下不可达**；若按字面实现，只能回退到函数级直调 + 打补丁（C-1 明示要消灭的模式），或把断言做成空转——本轮虽加了「禁止空转 skip」，但该禁令无法替代一条能真正触达 TTY 分支的路径。③文本已附「或声明 POSIX/WSL/ConPTY」兜底，故闭环可达，但把技术上无效的「管道模拟 TTY」当作 Windows 首选路径写入三处（L39/L83/L101），Step 3 若照字面取主路径即重演空转；「finally 还原 stdin/isatty」字样亦残留函数级 patch 的痕迹，与「真实交互测试」目标相抵，需澄清其作用对象（仅用于非 TTY 分支残留卫生，不得用于交互断言本身）。④修正要求：删去「stdin 管道=TTY 模拟」表述，Windows 单机具体路径钉为 ConPTY（winpty/pywinpty 伪终端，isatty True）或显式声明 CI 跑 WSL/POSIX（os.openpty + subprocess stdin=slave）；两选一后在 R-01/§6.2 同步。
- **confidence**：high（isatty 语义为平台级事实，代码门控已直读；属上轮同源问题第 2 次重开）。
