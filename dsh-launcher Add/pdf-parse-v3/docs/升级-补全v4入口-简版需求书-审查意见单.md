## 二、严重（Severe）

### [严重-2.1] §6.3 验收指标框架第 3 条的弹选场景列举与 §3.4/R-05 边界及冻结设计相矛盾

- **anchor**：`升级-补全v4入口-简版需求书.md` §6.3（"降级弹选：在'无 key / --no-egress / 模块缺失'三种模拟下……必须显式输出降级征询"）↔ 同文 §3.4（"整管线能力不可用（如 v4 全链不可跑）……页/表级视觉不可用维持自动本地兜底+诚实标记（FR-D7，不弹窗）"）↔ R-05（§5 表）。
- **basis**：本对象 §3.4 把"弹选"限定为**整管线能力不可用**，并把"页/表级视觉不可用"归入 **FR-D7 自动本地兜底、不弹窗**。但 §6.3 把 **"无 key"与"--no-egress"** 也列为触发"必须显式输出降级征询"的模拟情形。而冻结依据明确将这两者按**页级视觉自动降级**处理：需求书 §3.1/§8 与 FR-D7（"视觉不可用时（无 key/无额度/超预算/断网）视觉环节自动降级为本地管线+诚实标记+跳过，不阻塞全流程"）；设计 §10 异常总表 `VisionError(no_key/egress_blocked/budget_exceeded)→FR-D7：本地管线+诚实标记`；设计 §8.4 S2-R4（--no-egress 下低信号区/hint 阳性表 → status=uncertain + 声明，**非弹窗**）。同一对象 §4-3 又主张"已冻结 v4 架构决策不重开"。故 §6.3 与 §3.4 在**同一文档内部**冲突，且对"无 key/--no-egress"的定性**重开**了冻结的 FR-D7 语义，构成边界混淆。此外，--no-egress 由用户显式传入，意味着用户已表达"不出域"意愿，此时再弹"继续/降级/取消"在语义上自相矛盾。
- **建议处置**：把弹选情形严格限定为**整管线结构性不可跑**（如 M1/M2 缺失、orchestrator 启动门失败、整册无法产出 v4.0 的启动级故障）；"无 key/--no-egress"若按 FR-D7 处理为页级自动本地兜底+标记（不弹窗），或仅当"整册无任何页能产出 v4.0"（文档形态与视觉可用性组合后确为全链失败）时才升为弹选，且须在 §3.4 给出该判定口径并全篇统一。
- **confidence**：高

### [严重-2.2] R-05 与 §6.3 的验收用语"弹选项/明确告知"弱化用户硬性裁决口径（"弹选择项 + 用户选择才能降级"）

- **anchor**：`升级-补全v4入口-简版需求书.md` R-05（§5 表）："模拟 v4 不可用→不静默产出 v3.0；弹选项/**明确告知**后方可降级"；§6.3："必须显式输出降级征询（**选项/告知**）后才可继续"。
- **basis**：用户裁决口径②原文："**降级用 v3 必须先给用户弹选择项，用户选择才能降级，否则无感**"。§3.4 的目标定义忠实体现（"先弹选项由用户确认：继续解决依赖/显式降级并告知产物差异/取消"），但 **R-05 与 §6.3 的验收判定**将"明确告知（仅信息，不需用户选择）"与"弹选项（需用户选择）"并列，允许仅"告知"即通过验收。若实现选择"仅告知"路径，用户仍未被授予选择权——这与"否则无感"的升级动因相悖，且验收条目（它是本次升级核心新需求的**可测试守门**）放过了低于裁决口径的实现。本次升级的动因正是"继续用 V3 是不对的……否则无感"，验收应收紧而非放宽。
- **建议处置**：验收判定明确为"**必须弹出选项且须经用户选择**"；仅在**非交互上下文**（如管道/批处理无 TTY 且无法交互）时，作为**显式声明例外**允许"告知+默认不降级或取消"，并单独标注该例外的触发条件。
- **confidence**：高

### [严重-2.3] 只主张修订 §3.3-2，未处理 §3.1"全流程全自动"与 R-05 弹选的同类冲突，v2.4 修订稿仍将自相矛盾

- **anchor**：`升级-补全v4入口-简版需求书.md` §2 VG-5（"原需求书 §3.3 非目标 2'任何需要人工点选/交互的流程（全自动闭环）'是此行为的**需求侧根源**，本次须修订"）↔ §3.4（"（新需求，修订 §3.3-2）"）。
- **basis**：R-05"整管线降级弹选"引入的**人工点选/交互**，直接违反的不仅有需求书 §3.3-2，还有**§3.1 总体目标"全流程全自动"**（需求确定书 §3.1）。对象只点名修订 §3.3-2，未同样消解 §3.1。若 v2.4 仅改 §3.3-2 而 §3.1"全流程全自动"原样保留，修订稿内部（§3.1 ↔ R-05）仍冲突；对象 §4-6"非目标 6：页/表级视觉兜底的弹窗化（维持自动，避免破坏全自动闭环）"还复用了"全自动闭环"作为立论，而目标 4 恰恰打破"全自动闭环"，同文对"全自动闭环"这一不变量的使用口径前后不一。此外，VG-5 把行为根源归因于**非目标条文**属于过度归因：可观测到的"静默降级为 v3"的行为根源是 **v4 管线未通（M1/M2 缺失、MS-1 骨架）+ SKILL.md/回退逻辑静默转 v3**，需求书非目标条文只是设计哲学表述，不直接"造成"运行行为。
- **建议处置**：在 v2.4 修订中将"全流程全自动"消歧为"**正常路径全自动；整管线降级为显式同意例外**"，或对 §3.1 作出等价限定；并弱化 VG-5 的因果表述（改为"需求侧表述与本次降级显式化要求存在张力，需修订"，而非"根源"）。同时使 §4-6 的"全自动闭环"立论与目标 4、§3.1 修订后口径一致。
- **confidence**：中（§3.3-2 修订之**必要性**为高置信——R-05 确实引入人工交互，与 §3.3-2 显式冲突；但对 §3.1 必然冲突的判定为中，因"全自动"可被合理解读为"正常路径自动"，故评为中）。

- **anchor**：`升级-补全v4入口-简版需求书.md` §2 VG-6（"M3 textlayer 等下游模块已实现但 orchestrator 未接入（文字层 PDF 无 v4 通路）"）↔ assets\v4\orchestrator.py（仅 import vision_client、调 glm_parse_page）↔ assets\v4\pipeline.py（离线全链：table_adapter→gate→ladder→structurer→quality）。

- **confidence**：高

### [轻微-3.3] 验收指标框架 §6.2/§6.4 存在空集/弱断言通过风险，且未内建"指标不得真空"守卫

- **anchor**：`升级-补全v4入口-简版需求书.md` §6.2（"每页 routing.method=glm、台账记 cost/usage；**表 status 非空**"）、§6.4（"hash 数值比对等真实断言（**无假绿灯**）"）。
- **basis**：①"表 status 非空"是弱断言：`status∈{unreadable,uncertain,...}` 亦属"非空"，若整册表全部标记为不可读/不确定仍可通过；且零表（空集）时该子句真空通过。②§6.4 的"无假绿灯"是元表述（quality 声明），不是可测判据；框架未枚举需测量的**硬指标**及其**非真空分母**。本文档同一升级历史上已发生**假绿灯阻断**（v4-最终集成交付-G008-自证声明 第 11 行：defect_capture 分子恒=分母、cost_observable 空账=1.0、conservation 空写回=1.0 曾使硬指标真空通过），本文 §6 未在框架层内建"指标不得真空（分子=分母/空集过 1.0 即判失败）"守卫，存在再次放行"假绿灯"的框架级风险。
- **建议处置**：§6 增加一条总守卫（"任一硬指标若因空集/分子恒等分母而得到 1.0，按失败计，不得放行"）；§6.2 将"表 status 非空"改为"存在表时 status 分布与 marked/unreadable 原因齐备，且按真实台账统计"；§6.4 明确列出硬指标清单与各自非真空分母（可延续"细化任务书定口径"，但框架应点名）。
- **confidence**：中（空集风险为低置信、弱断言为中置信；因对象声明"细化任务书定口径"，框架级守卫缺失评为中）。

### [轻微-3.4] 新编号体系 R-01..R-08 与上游 FR-<域><序> 的关系、以及 §5 与 §6 的对应未交代

- **anchor**：`升级-补全v4入口-简版需求书.md` §5（R-01..R-08）↔ 需求确定书 §5 编号规则（`FR-<域><序>`，域 A–G）↔ §6（验收框架五条）。
- **basis**：对象引入独立命名空间 `R-01..R-08`，与上游 `FR-<域><序>` 体系并存，但未说明 R-xx 在 v2.4 修订稿中如何并入 FR 体系（如 R-05 是否新立 FR 编号、归属哪一域），也未标注 §6 五条指标分别校验哪些 R-xx。同文档内 §5 与 §6 对应关系不明，且"R-"前缀与既有"FR-"前缀的语义关系未消歧，跨文档交叉引用时有混淆风险。
