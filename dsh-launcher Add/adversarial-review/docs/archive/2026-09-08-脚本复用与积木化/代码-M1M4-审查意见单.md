## 二、严重（4 条，需在本里程碑内关闭）

### S-1 候选队列以纯 name 键写共享目录 → 跨任务同名脚本被静默丢弃候选

- **anchor**：`_collect_candidates.py` L19（`QUEUE = SKILL / "var" / "queue"`，跨任务共享）、L95（跳过判据 `f.name == f"{name}.json"`）、L110-111（`(CAND_DIR / f"{name}.json").write_text(...)` 只以 `{name}.json` 为文件名，不带 task_id）。
- **basis**：spec §4.2（候选含 `task_id`，NEW-sA「task_id 生产源=收集器」）与 §3（`queue\candidates\<name>.json`）；§8 第 3/4 条采集链要求为每个任务的脚本产候选并可晋升。当前候选文件键=纯 name、目录全局共享 ⇒ 任务 A 收集 `l0_registry_check` 后，任务 B 的同名脚本（跨任务通用脚本恰恰最易重名，本设计核心复用对象即为 `l0_config_keys`/`l0_registry_check` 这类通用名）在 L95 被判「已收集」而跳过，永不生成候选 → 永不晋升 → 其复用永不计入 R7 台账。实测 `var\task-scripts\` 下已有 `pdf-parse-v3` 与 `fire-xlsx-zhuze-xuebu` 两任务目录并存，证明共享队列真实存在二次任务碰撞面。
- **confidence**：高（机制与依据明确，且存在多任务目录佐证）。

### S-2 收集器裸跑脚本、不传脚本所需参数 → arg 依赖脚本 regression 失真被误拒

- **anchor**：`_collect_candidates.py` L60-69（`subprocess.run([sys.executable, str(script_path)], ...)` 无实参）、L98（`reg = _run_evidence(sp)`）。
- **basis**：spec §5 W2「regression=运行结果快照」、§4.2 regression 字段口径。试点 `registry.json` 中 `l0_config_keys` 的 run 明确为 `python .../l0_config_keys.py C:/.../pdf-parse-v3`（必带被审对象根参数）。已核读 `l0_config_keys.py` L15-17：`len(sys.argv)<2` 即打印 usage 并 `return 2`。`_run_evidence` 以裸脚本运行 → returncode=2 → `passed=False` → `sediment_run.phase_S3` L434 将其移入 `failed\`，该「可复用范例脚本」永不晋升。收集器未按 registry/docstring「复跑」行补参，arg 依赖脚本的 regression 必然失真，破坏 M2 晋升链对该脚本的闭合。
- **confidence**：高（已实读脚本确认需要 `argv[1]`）。

### S-3 积木胶水检测遗漏模块级函数/类引用 → 可能产出非纯函数坏积木

- **anchor**：`_extract_bricks.py` L76-85（`_top_level_assigned` 仅收 `ast.Assign`/`ast.AnnAssign` 目标）、L104-111（`glue_refs = used & assigned`，assigned 再减 imports）。
- **basis**：R4 硬约束 a（抽取必须剥任务特定逻辑、产物为参数化纯函数）；spec §5 W4。`_top_level_assigned` 未收集模块级 `FunctionDef`/`ClassDef`/for 赋值名，故目标函数调用同模块的 helper 函数/类时不会进入 `glue_refs` ⇒ 未被判为胶水 ⇒ 写入的积木模块不含该 helper ⇒ import/调用即 NameError，产物非纯函数、直接违反硬约束 a。自测仅用常量胶水（`BASE`），未覆盖「函数级胶水」，与本条缺口完全对应。
- **confidence**：中高（机制明确，属实缺口）。

### S-4 积木同名不同内容 → 覆写模块文件并产生重复 code_path 条目

- **anchor**：`_extract_bricks.py` L129-147（去重仅按 `content_hash` 判 hit L132；L144 `(BRICKS_ROOT/f"{func_name}.py").write_text(module)` 无条件覆写；L145 `container["bricks"].append(brick)` 无条件追加）。
- **basis**：spec §4.4（同名去重隔离）与 R4（内容哈希去重+幂等）。两任务提取同名函数（如 `norm_num`，跨任务通用函数最易同名）且内容不同时：hash 不同 → 不命中 → 用同一 `code_path` 覆写模块文件 → registry 出现两条都指向同一文件的条目，首条「所指文件」实为次条内容，`_gen_catalog` 随之呈现重复/失真。自测仅覆盖「同内容幂等」，未覆盖「同名异内容」。
- **confidence**：高。

## 三、轻微（7 条，验收前可合并处理）

### m-1 validate_candidate 确定性字段强制 code_path、不认 code 二选一
- **anchor**：`_collect_candidates.py` L22（`DETERMINISTIC` 含 `code_path` 无 `code`）、L31-34。
- **basis**：spec §4.2「code_path 或 code（内联源码）二选一」、§8 第 3 条「R2 schema 校验通过」。校验器强制 `code_path` ∈ 确定性字段，code-only 候选被判「确定性字段缺 code_path」。当前自动收集恒写 code_path 故不触发；若手工/他路产 code-only 候选则校验误拒。属校验器与自身 schema 的不自洽。
- **confidence**：中高。

### m-2 phase_S3 未实现 task_id 缺省注入
- **anchor**：`sediment_run.py` L413（`"task_id": cand.get("task_id")`）。
- **basis**：spec §5 W3「候选缺 task_id 则取被审对象名注入」。当前缺则记 `None`，不注入被审对象名；`test_2_1_phaseS3` 候选恒带 task_id，未覆盖该分支。
- **confidence**：中高。

### m-3 跨来源 hash 不一致（文件字节 vs 内联文本）致幂等去重跨来源失效
- **anchor**：`sediment_run.py` L403-411（内联 `sha1(code.encode)`；文件 `sha1(open(cp,'rb').read())`）。
- **basis**：spec §4.3/§6 c-m1「hash=内容 sha1」应来源无关。同脚本分别以 `code` 与 `code_path` 两来源注册时，内联文本 ≠ 文件字节 ⇒ hash 可能不同 ⇒ L421 按 hash 去重在跨来源时不命中。自动收集恒走 code_path，故常规不触发。
- **confidence**：中。

### m-4 catalog「作用」列实际显示 changelog 而非用途
- **anchor**：`_gen_catalog.py` L39-42（`{e.get('changelog','')}` 填入「作用」列）。
- **basis**：spec §5 W5（清单内容=积木名→作用→…）、R5。积木 schema §4.4 无 description/作用字段，本列实际显示「提取自 …」；人读清单无法说明积木干什么。自测仅断言 `"norm_num" in md`（name 列命中），未验证「作用」列语义。
- **confidence**：中高。

### m-5 register_l0 覆写容器 target 元数据值
- **anchor**：`_registry_io.py` L85-86（`_merge_meta(cont, {"namespace":"code","target":str(task_id),...})`）。
- **basis**：spec §4.1/§6 s2「任何写回不得覆盖容器元数据」；试点 `target="pdf-parse-v3 v4 管线成果"`（描述性）。`register_l0` 无条件 `target=str(task_id)`，会把描述性 target 覆写为任务名；`updated`/`location_rule` 因值为 None 走 `_merge_meta` 的 `is not None` 保护未被覆盖（正确），唯 `target` 例外。
- **confidence**：中。

### m-6 extract_brick(admission=None) 抛 AttributeError 而非诚实 refuse
- **anchor**：`_extract_bricks.py` L91-93（`admission.get('cross_task',0)` 在 `admission` 为 None/非 dict 时崩溃，尽管 `admission_ok(None)` 返回 False）。
- **basis**：函数签名 `admission: dict` 无默认；docstring 承诺「None+reason 诚实返回」，但 None 实际触发 `AttributeError`。自测/CLI 恒传 dict，未覆盖此边界。
- **confidence**：中高。

### m-7 收集器与 phase_S3 状态基路径可能分叉
- **anchor**：`_collect_candidates.py` L19-21（`QUEUE = SKILL/var/queue`，硬编码技能根）；`sediment_run.py` L390（`state/queue/candidates`，state=resolve_state_dir）。
- **basis**：`sediment_run.resolve_state_dir` 会回落 `~/.adversarial-review`（若 `ADV_REVIEW_HOME` 设置或技能根 var 不可写）。此时收集器写 `<SKILL>/var/queue` 而 phase_S3 读 `<state>/queue`，候选互相找不到。常态同路径故不触发。
- **confidence**：中。

## 四、建议（3 条）

### su-1 `_inject_default` 值格式歧义
- **anchor**：`_extract_bricks.py` L150-155（`param + "=" + str(value)`）。
- **basis**：字符串型默认值需调用方预加引号（如 `'""'`）；传 `str("x")` 得 `x` 而言 `s=x` 非法。自测仅测 int 默认值。建议：defaults 值以 JSON 字面量/repr 解析再注入，并回填到 `_defval` 口径。

### su-2 register_l0 的 run 不捕获脚本所需参数
- **anchor**：`_registry_io.py` L77（`"run": f"python {sp}"`）。
- **basis**：与 S-2 相关；试点 `l0_config_keys` 需 arg，`register_l0` 产出的 run 缺参（其触发链同样会让 `run_registered`/`l0_registry_check` 无法照 run 直跑）。建议 register_l0 增可选 args 或从 docstring「复跑」行取参。

### su-3 节点测试覆盖缺口（正对应 S-1..S-4 边界）
- **anchor**：`tests_node\test_2_1_phaseS3.py`、`tests_node\test_4_2_snapshot.py`。
- **basis**：两测试断言均非恒真、属真实校验（结论成立），但 `test_2_1` 未测跨任务同名碰撞、跨来源 hash 不一致、task_id 缺省注入；`test_4_2` 未验 `est_saved_tokens` 计算口径与 `reused_count` 对 `reused_scripts[]` 长度的一致性（validate 亦未校验该一致性）。建议补对应反例。

## 五、总体结论（可否继续）

- **阻断=0**；机制主链路（registry 原子写保 meta、register_l0 幂等、run_registered 两分支、found_issues 回填、参照 S3 去重/归档、积木准入、catalog 生成、快照 reuse_ledger 校验+回填）在自动收集这一条主路径上可运行，M3 机制验证（合成夹具）不因 4 项严重而必然走空。
- **4 项严重需在本里程碑（M5 试点/WBS-5.x）内关闭**，否则首次真实跨任务复用即暴露：
  - S-1 会让「第二个任务」的同名脚本永不产候选/晋升，直接削弱 R2/R3/R7 闭环；
  - S-2 会让试点自身范例脚本 `l0_config_keys` 在采集链被误判失败，破坏 M2 晋升链与「可执行」验收语义；
  - S-3/S-4 会让 R4 产出**坏（非纯/覆写）积木**，与「硬约束 a/b + 内容哈希去重」相悖。
- **判定**：可继续 M5 试点/WBS-5.x，但建议先于或伴随 WBS-5.x 关闭 S-1..S-4（尤其 S-2 会阻断试点脚本晋升、S-4 会产坏积木）；7 条轻微与 3 条建议可合并至 WBS-5.x 顺手处理，不构成阻塞。修复范围以本意见单为准，避免顺手改动。
