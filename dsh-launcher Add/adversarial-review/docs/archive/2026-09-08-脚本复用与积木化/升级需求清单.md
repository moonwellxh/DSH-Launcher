## 一、背景与结论

本次多轮审查实测现象：第一轮审查者写了 `review_replay_p87.py` 等重放脚本，第二轮审查者又自编了一套（`review_r2/`），重复劳动、白耗 token。

对照 skill 现状后确认（均已查证）：

- **skill 只实现了脚本泛化的「晋升收口」，缺「采集」与「积木化」两块。**
- 用户目标设计（按任务 A/B/C 分别存各自任务的测试脚本共享目录＋说明 → 同任务跨轮复用 → 沉淀时搜集「脚本＋测试问题＋环境＋测出的问题等维度」→ 拆解成通用函数积木放入skills下的特定子目录 → 并同步可用积木目录清单以便夸任务测试时复用）**是对的、比现状更完整**，但 skill 尚未落地。

## 三、需求清单

### R1 脚本落盘约定（采集层；已定稿，任务目录已裁决见 §七 R1）

- 目标：每轮审查产生的确定性验证脚本（L0）有固定落点＋文字说明，后轮可直接找到。
- 拟补：约定目录结构 `var/task-scripts/<task-id>/`；每脚本 docstring **四行模板（作用/输入/输出/复跑〔含依赖〕）**。
- 裁决（2026-09-07）：task-id = 被审对象名；试点期目录挂 `adversarial-review\var\task-scripts\`，跨技能通用化后再升共享区；轮次信息入 R2 的 version 字段，不设 round 子目录。

### R2 候选脚本字段规范（采集层；2026-09-07 补采集维度去向，闭合 A-S6/K3-s1）

- 目标：让脚本连同「要测的问题、测试环境、测出的问题」一起进入沉淀分析。
- 拟补：定义 `queue/candidates/*.json` 完整 schema：`name, ns, version, code_path（或内联 code，phase_S3 须兼容两种来源）, description, test_problem, environment, found_issues, regression{passed, evidence}`。
- **采集维度去向（2026-09-07 裁决）**：① `test_problem/environment/found_issues` 进入沉淀分析（S1/S2 导引单回写为 sediment 扩展，步骤 7 实现）；② 同任务跨次回查由**任务级 registry 条目可选 `found_issues` 字段**承载（schema 见 §七 R3，可选字段）；③ 作为 R4 拆积木的输入（哪些片段反复解决同一 test_problem）。
- 现状：仅 name/ns/version/regression.passed 被读取，其余未定义未采集。

### R3 注册表补脚本本体引用（复用层）

- 目标：让「运行 registry 中脚本」不再悬空。
- 拟补：registry 条目补 `code_path/entrypoint/hash`，明确 L0 脚本物理位置与运行方式。
- 现状：registry 只存名字。

### R4 积木化通用函数库（复用层；2026-09-07 依用户目标修订；补沉淀对象界定、两条硬约束、准入与单一位置）

- 目标：把高频脚本拆解为可组合的通用函数（积木），下次直接 import；**含跨任务复用**（用户目标终态）。
- 拟补：
  - **位置（定稿，闭合 A-S5/K3-m5）**：积木库 = **单一确定位置 `~\.agents\skills\_shared\bricks\`**（skills 统一共享根下；与任务级 `var\task-scripts\<task-id>\` 分离——任务目录放「该任务的脚本」，共享根放「跨任务通用函数」）。若主技能根迁移，积木库随之迁移一次并更新 catalog。
  - **准入（定稿，闭合 A-S2）**：片段晋升为积木须**持回归证据**（来源片段/脚本 `regression.passed` 且 evidence 可查），并过**准入计数**（跨 ≥2 任务被复用 或 同任务 ≥3 轮命中）——与 S3「回归通过才晋升」对等；无回归证明的片段不入积木库。
  - **命名/粒度**：纯函数级积木，`snake_case`＋语义前缀；docstring 同 R1 四行模板。
  - **动作（S3 扩展）**：沉淀时把任务脚本拆解/归并为积木（不只按 name 晋升整脚本）；**内容哈希去重**（依赖 R3 的 hash 字段），同函数重复晋升只更新引用不重复落盘（幂等）。
- **沉淀对象界定（2026-09-07 裁决，R4 的输入确认）**：沉淀对象**不是整条任务脚本**，而是「多积木拼接的非通用脚本」中**反复用到的通用片段**；沉淀动作 = 挑出这些片段 → 打磨为**可带参数调用**的通用函数；他人编写脚本时**直接调用或带参调用**，需要时可**扩展参数后再调用**。
- **硬约束 a（拆解边界，2026-09-07）**：抽取通用积木时必须**剥掉任务特定逻辑**，产物为**参数化纯函数**；任务特定部分**留在原任务脚本中作为「胶水」**，不得混入积木。
- **硬约束 b（参数机制，2026-09-07）**：积木函数形参**必须有默认值**（保证既有调用不被破坏）；**扩展参数属于版本升级**，必须在积木库 registry 中登记**版本与变更说明**。
- 待细化：积木粒度判定（何时该拆）、命名前缀表、归并规则。

### R5 技能级可用积木目录清单（发现层；2026-09-07 依用户目标修订）

  - **内容**：积木名→作用→适用 ns/任务→模块路径→entrypoint→单测/复跑法。

### R6 跨轮同任务复用通道（流程层）

- 目标：A2/A3 直接复用 A1 脚本，不必等「沉淀」。

### R7 复用收益可观测（控制论反馈层；2026-09-07 定稿口径，闭合 A-S3/S4 + K3-M2/M3）

- 目标：让「复用省了 token/不重复推导」**可计量可验证**，否则新目录可能成无人复用的摆设。
- **度量归属（定稿，消除与 R3 双轨冲突）**：`hits`/`false_positives` **记在技能级晋升注册表条目**（与 sediment_run.py phase_S3 落点一致），**任务级 registry 不记**。
- **写入者（定稿）**：
  - `hits`：**编排者每代跑一次已登记脚本即 hits+1**（与 R6「编排者先查 registry 并代跑」绑定同一触发点）；累计在技能级条目。
  - `false_positives`：收尾/复审判定某脚本输出为误报时**回写该脚本技能级条目 +1**（依据=快照 issue 的 false_positive 归属到脚本）。
- **防重写估计 token（定稿分母口径）**：基线 = 按脚本长度估算单次重写成本 `W ≈ ceil(字符数 / 2) token`；防重写节省 ≈ `复用脚本数 × W`（相对量，注明估算口径，非精确）。
- **每轮复用台账**：`{round, reused_scripts[], new_scripts[], reused_count, new_count, est_saved_tokens}`；并入本轮 snapshot（协议 §7.1 快照 schema 于技术设计期增复用字段，步骤 7 实现）。
- 依据：控制论反馈闭环——系统有效性的传感器数据，决定 R1/R3/R4 是否真降本。

### R3 registry 补脚本本体引用（已定稿；2026-09-07 补 hash 与示例路径，闭合 A-S1/K3-m2/m3）

任务级 `var\task-scripts\<task-id>\registry.json` 条目 schema：

```jsonc
{"name": "l0_xxx", "ns": "code",
 "code_path": "<绝对路径>/var/task-scripts/<task-id>/l0_xxx.py",  // R1 裁决：绝对路径（可执行事实源）
 "entrypoint": "main", "run": "python …", "purpose": "…",
 "hash": "<内容 sha1>"}                                            // 补：R4 内容哈希去重依赖字段
```

「运行 registry 中适用命名空间的脚本」= 按 `code_path`+`run` 直接执行，不再悬空。

**双轨语义（2026-09-07 裁决；闭合 A-S1 互指矛盾）**：
- **任务级 `var\task-scripts\<task-id>\registry.json` = 可执行事实源**（脚本真实存在、可直接运行，含 code_path/entrypoint/run/purpose/hash）。
- **技能级 `var\registry\scripts.json` = 晋升注册表**（S3 晋升后写：name/ns/version/**code_path/hash**/hits/false_positives/registered_at——**含 code_path+hash 指回任务级**，互指可实现）。
- 两者**不合并**，靠 `code_path`（+hash）互相指向；「任务级是事实源、技能级是索引」各自职责不重叠。

## 八、两级资产模型与第一性/控制论落点（2026-09-07 依用户目标细化）

### 模型（对齐用户目标）
```
任务级（per-task）          技能级（cross-task，skills 下特定子目录）
var/task-scripts/<task-id>/  <积木库>/
  l0_*.py（本任务）          通用函数积木（纯函数，可跨任务 import）
  registry.json（任务级发现） catalog.md/json（技能级可用积木清单，随 S3 同步）
  README.md
链路：任务落盘(R1) → 候选字段(R2) → 回归晋升(S3，只晋回归通过) → 拆解为积木(R4) → 技能级清单(R5)
复用：同任务跨轮(R6，编排侧先查任务 registry) ＋ 跨任务 import 积木(R8，先查技能级清单)
```

### 第一性原理
验证资产价值 ∝ 复用次数 × 判断独立保持时长。浪费本质=同一确定性计算被反复再推导。
系统使命：**一次推导、多地复用、保持独立、浪费可计量**——任何需求若不能让这四句变强，即非必要。

### 系统控制论落点
| 角色 | 对应 |
|---|---|
| 被控对象 | 再推导率 / token 浪费 |
| 传感器 | 回归证据（S3 regression.passed）、registry `hits/false_positives`、每轮「复用 vs 新写」计数（R7） |
| 控制器 | 落盘义务（R1）→ 复用顺序（R6 编排侧先查）→ 有界晋升（S3）→ 跨任务清单同步（R5/R8） |
| 执行器 | 评审者（独立解读）/ 编排者（L0 代跑） |
| 反馈与校正 | false_positives 回写降权；晋升幂等（内容哈希去重，防重复注册） |
| 独立性不变式 | 脚本/积木**只编码「输入→确定性计算」，禁含预期结论**；预期由当轮评审者独立形成比对（贯穿两级，R6/R8） |

- 修正 R5：从"任务/含糊人读清单"提为"技能级跨任务可用积木清单，随 S3 同步"。

## 九、需求→执行体分工（脚本优先，必要时才用大模型；2026-09-07）

**边界判据（第一性）**：凡「输入→确定性输出」可编码 → **脚本 S**（零 token、可复跑、可观测、回归可证）；
凡需**语义判断 / 独立结论 / 新内容创作** → **大模型 LLM**（且审查判断强制独立：L1/L2 由独立子审查者执行）。
**禁止**：用 LLM 重算脚本已覆盖项、用脚本内置预期结论（观测独立性不变式）。

| 需求/环节 | 执行体 | 说明 |
|---|---|---|
| R1 条文 | 一次性文本；保障=**S** | `l0_registry_check.py`（registry↔文件一致、docstring 四行） |
| R2 | **S** 主体 + LLM（语义字段） | phase_S3 读新字段=脚本；candidate `description/test_problem/found_issues` 语义=评审者 LLM（必要；found_issues 回填前允许 null+pending_review，见 spec §4.2） |
| R3 | **S** | registry 落盘/校验/「运行 registry 中脚本」全确定性 |
| R4 | **H** | 提取/去重/归并=脚本；「何时拆积木」决策=LLM（低频，有命中数据才值得） |
| R5 | **S** | catalog 由脚本从 registry/积木目录确定性生成同步 |
| R6 | **S**（条文一次性） | 编排者先查 registry 直接跑脚本 |
| R7 | **S** | hits/false_positives/每轮复用 vs 新写=确定性计数 |
| R8 | **S**（条文一次性） | 查清单/import=脚本 |

**控制论注释**：脚本 = 确定性传感器/执行器（零 token、可复跑、可观测）；LLM = 仅在「语义判断 + 独立性强制」处作为观测通道出现。凡能被脚本替代的环节，一律不耗 LLM——这正是「省 token」的第一性落点。
