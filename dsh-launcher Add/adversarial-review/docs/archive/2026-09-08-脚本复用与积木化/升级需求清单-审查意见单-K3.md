- anchor：《升级需求清单.md》§三 R1（39 行）、§七 R1（125 行）、§九（217 行）；对照 SKILL.md §2（41 行）、l0_registry_check.py（14、55 行）
- basis：R1（39 行）称「docstring 四行模板定稿：作用/输入/输出/复跑方式/依赖」，此处为**5 个组件**；§七（125 行）为「作用/输入/输出（一行可 grep）/复跑命令与依赖」=4 组件；SKILL.md §2（41 行）为「作用/输入/输出/复跑命令/依赖」=5 组件；而 R1 保障脚本 l0_registry_check.py（14 行）`DOCSTRING_LINES=("作用","输入","输出","复跑")` 仅强校验 4 项、**不含「依赖」**（52 行也只对 l0_* 强约束）。「四行」与组件枚举不一致，且 R1「docstring 四行」保障（§九 217 行）实际比声明的模板弱——漏校验「依赖」这一要求项。

- basis：R2 采集了 test_problem/environment/found_issues 等「多维度」，但这些字段只存在于 queue/candidates（S3 晋升后整文件被移入 queue/done，404 行）；任务级 registry（154–155 行）只记 name/code_path/entrypoint/run/purpose，技能级 registry（162 行）只记元数据。故「该脚本测什么/在哪测/测出哪些问题」在 R2⊗R3 双轨下没有可查询的承载结构，同任务跨次复用只能凭 code_path 找到脚本、查不到采集维度。建议在任务级 registry 或技能级 catalog 补一个「采集维度」字段承载。

## 五、结论摘要（是否可进入步骤 3 技术设计）

**总体**：需求清单的目标链覆盖完整，思路正确、第一性/控制论落点清晰；但**存在 1 阻断 + 3 严重**，均为「已定稿/已落地」声明与实际操作条文、实测文件系统脱节的**一致性/可实现性**问题，主要落在 R1 与 R3 的「SKILL.md §2 未被真正同步」及 R7 的「度量无数据源」。这些问题不修正，会把步骤 3 技术设计建立在「悬空指令已解决、收益可计量」的虚假前提上。

逐项证据与缺口：

- **R1**：方向正确、迁移已执行（var\task-scripts\pdf-parse-v3\ 实测成立，registry 绝对路径、l0_config_keys 传参根）。**可进入步骤 3，但有前置缺口**：SKILL.md §2 现行条文仍是旧「审查脚本/」且不写 var\task-scripts（M1，B1 同族），需先把操作条文与裁决②/決策① 统一。另 docstring「四行 vs 五组件」及保障脚本漏检「依赖」（m1）需一并定稿。
- **R2**：schema 完整涉及「多维度采集」，方向正确。**可进入步骤 3，但脚本侧（phase_S3 读取新字段）属 P0 待做，且 schema 示例仍是旧「审查脚本」命名（m3）**；采集维度建议补一个可查询承载（s1）。
- **R3**：双轨语义（任务级=可执行事实源、技能级=晋升索引、靠 code_path 互指不合并）是清晰正确的设计。**但当前被「R3 已入 SKILL.md §2」误标**——SKILL.md §2（36/42 行）仍指向技能级索引且无双轨（B1）。**进入步骤 3 前必须**：① 更正文头「已入 §2」的说法；② 把 SKILL.md §2 L0 运行指令改为「先查任务级 registry、code_path+run 直跑」；③ 补 hash 字段（m2，R4 去重依赖）。
- **R4**：目标（skills 子目录积木库、拆解/去重/幂等、硬约束 a/b、沉淀对象=通用片段）符合用户目标终态，理念正确。**可进入步骤 3 作为「骨架+占位」**（P1 已明确），但积木提取/去重/catalog 生成脚本均不存在（m5），需在设计里给出可落地的 phase_S3 扩展与积木库目录路径（现为「<某技能根>/_shared/bricks/ 或技能树统一共享库」二选一、未定）。
- **R5**：技能级跨任务清单、随 S3 同步，方向正确。**可进入步骤 3（骨架+占位）**，但 catalog 生成脚本缺失（m5），且 catalog 与积木库目录未定具体路径。
- **R6**：**已真正落地**（SKILL.md §2 脚本复用段、§3.5 复审独立性，均实测存在），一致性良好，**可直接进入步骤 3**（对已落地条文做形式确认即可）。
- **R7**：**不宜直接进入步骤 3**——hits/false_positives 放置与 R3 双轨冲突（M2）、hits 无写入者与 false_positives 不递增、「回写降权」无执行器、台账字段名/落盘位置未定（M3）。需先在清单内自洽（明确 hits 计数的触发点=编排者代跑、false_positives 的写回机制、台账字段并入 §7.1 快照的确切 schema），再谈设计；否则「收益可观测」是空承诺。
- **R8**：目标正确，**可进入步骤 3 但作为依赖项尾随**——依赖 R4/R5 至少存在骨架目录（已述），且条文锚点须借 R1/R3 条文定稿后再落（s3）。

**结论**：需求清单**暂不建议整体直接进入步骤 3 技术设计**。先闭合 B1+M1（R1/R3 与 SKILL.md §2 实际操作条文的同步）与 M2+M3（R7 度量的自洽与数据源），并补 R4/R5 的积木提取/catalog 生成器的实现接口后，R1/R2/R3/R6 可立即进入设计，R7/R8 依前述闭合后跟进。
