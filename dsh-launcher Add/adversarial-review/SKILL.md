# adversarial-review（对抗性审查与沉淀迭代）

本技能用于：对**具体产出物**做分级对抗审查、驱动修复闭环、并在多轮运行中沉淀前置导引单与脚本资产以持续降低 token 消耗。**不适用**于：无具体对象的一般问答；用户明确说"不用审"的场景。

## 0. 启动判定（先做，不审查先判定）

1. **对象与命名空间**：判定审查对象类型 → 命名空间（regulation 规范类 / document 文档类 / code 代码类 / 不明→general 通用层并告知用户）。
2. **模式**：默认"审查+修复闭环"；用户明示"只审不修"→ 仅报告模式。用户输入"本次不审"→ 退出。
3. **生成阶段注入判定**：若当前任务是**生成**交付物且命中白名单（对外文档/规范条文/长文档/代码）或历史同类曾被送审 → 运行 `python3 scripts/guide_inject.py --ns <ns> [--budget 600]`，用其 `block` 字段作为注入块，并告知用户"本成果完成后将进入对抗性审查"。**禁止手写/目测截取导引单**——截断顺序必须由该脚本确定性计算（算法与截断顺序见 protocols.md 4.8）。四条硬约束（owner 裁决 2026-09-10）：
   - **位置＝生成动作前的最后位置**：读完资料、开始撰写之前才注入，**不放在上下文前部**。理由：前缀缓存规则是"改动前部任意字节，其后全部失效"（protocols 6.2），尾部注入使导引单变更只失效其自身，而非整个任务上下文。
   - **历史不复改**：本会话中已注入过的导引单文本**永不回改**；条款更新一律以增量补丁（新增行/变更行/作废行）追加。
   - **同会话不重复粘贴**：再次命中生成任务时，无变更只发一行指针（"导引单已在本上下文，已注入 N 条"）；有变更只发增量补丁。
   - **截断可见且入账**：`dropped` 非空时，截断说明行随 `block` 一并注入，并把 `dropped` 写入本轮快照的 `guide_dropped` 字段（供沉淀端排除降权候选，见 M5）。
4. **显式命令**：用户逐字输入"执行沉淀"→ 跳转第 7 节，不启动审查。
5. **会话级覆盖（停止沉淀，owner 裁决 2026-09-10）**：用户说"停止沉淀"或"停止本次会话的沉淀"→ 落盘 `var/overrides.json`：
   ```json
   {"stop_sediment": {"ns": ["document"], "until": "<ISO8601>", "reason": "…", "created_at": "<ISO8601>"}}
   ```
   `ns` 省略即抑制全部命名空间；`until` 缺省取"当前时间 +24h"（"本次会话"口径），用户给了明确期限则用其值。写入后 `sediment_check.py` 对该命名空间返回 `signal=none`，并在 `signals` 中以 `suppressed` 留痕、在顶层 `suppressed` 汇总；到期自动失效并以 `override-expired` 留痕。**这是机械保障：不得以"我记得用户说过"替代落盘。**

## 2. 分层审查工作流

**审查执行独立性（强制，首次与复审均适用）**：L1/L2 的模型判断须由**独立子审查者**执行——新建 `subagent`（**不 fork** 本会话上下文），只喂必要数据：对象当前全文＋交叉核对依据清单＋（复审时）上轮意见单；**不喂**编排者/作者在本会话的任何推理、上轮结论或他人复审结论。L0 确定性脚本由编排者侧运行（零模型判断，不受此限）。并行判据（3 万字符或 10 章节）满足时再分解为多个子审查者并行，仲裁见 protocols.md 4.6。此要求不以对象规模为豁免：编排者上下文可能已含作者推理，对象再小也有自我确认风险。

**子审查者调度纪律（强制，2026-09-12 立规）**：独立子审查者一律**后台发起**，发起后去做别的事（**不得同时修改被审对象**，否则所喂「对象当前全文」失效）、等宿主在子代理结束时**自动通知**；**禁止轮询其进度**——不得循环查询状态、不得反复读取其中间输出、不得以「催办／发收尾指令」追加轮次换取更早产出。仅当下一步动作确实依赖其结论时，允许**一次**阻塞等待（前台发起，或宿主支持的等待式取回；**不得以循环查询代替**）；超时（上限见 §1 参数表「子审查者等待上限」）未回 → 记为**调度超时**：输出遗留清单交用户裁决，不得空转重试（与 §3.6「超 5 轮熔断」不是同一机制）。依据：催办要重算子审查者整段上下文、轮询读取则在编排者侧重复计费，两者都是重复开销，且不改变其产出时间。

**阶段 L0（确定性检查，零模型判断）**：先查**任务级 registry**——`<审查技能 var>\task-scripts\<task-id>\registry.json`（可执行事实源，条目含 code_path/run）；按其 `code_path`+`run` 运行适用本任务的脚本，脚本输出即证据。技能级 `var/registry/scripts.json` 仅为晋升注册表（元数据索引，含 code_path/hash 指回任务级），**不直接运行**。禁止用模型重算脚本已覆盖的检查项。

**脚本复用（不破坏独立性，避免过度隔离）**：L0 确定性脚本（重放/计数/机械校验等，只编码「输入→确定性计算」）可**跨轮、跨复审复用**，不要求子审查者重写。编排者侧应把**上轮已产出的 L0 脚本**（如重放脚本、隔离不变式校验）作为可复用资产喂给子审查者，或由编排者侧代跑；子审查者只做增量（新增测试用例，属模型判断须新鲜）＋独立解读输出并形成结论。**唯一禁止**：复用「硬编码了结论断言的脚本」——脚本只能编码计算、不得内置预期结论；预期值由本轮子审查者独立形成后与脚本输出比对（防观测独立性污染）。

**L0 脚本持久化与复用（R1/R3 定稿并同步《升级需求清单》裁决②/③，2026-09-07）**：
- **落盘义务（评审者/编排者双方）**：新写的确定性校验脚本**一律落盘到任务级目录 `var\task-scripts\<task-id>\`**（task-id=被审对象名；试点期挂本技能 adversarial-review 的 var 下，不污染被审对象树），命名 `l0_<用途>.py`；脚本内 docstring 四行模板写明 作用/输入/输出/复跑（含依赖）。**禁止把一次性脚本丢进临时目录后丢弃**（否则下轮重写、token 浪费）。
- **registry 双轨（任务级=可执行事实源；技能级=晋升索引）**：任务级 `var\task-scripts\<task-id>\registry.json` 每条须含 `name/ns/code_path(绝对)/entrypoint/run/purpose/hash`——「运行 registry 中脚本」按 code_path+run 直接可跑；技能级 `var/registry/scripts.json` 为 S3 晋升注册表，条目含 `code_path`（指回任务级脚本）+`hash`（内容哈希）+`hits/false_positives/registered_at`，两者靠 code_path 互指、不合并。
- **复用顺序**：编排者每轮先查任务级 registry → 已登记项直接代跑（代跑一次即 hits+1，R7）或喂评审者，不重写；评审者新写脚本须落盘并登记。
- **增量复审**：复审者沿用 §3 第 5 条——把上轮 L0 脚本随意见单喂给复审者「可复用/扩展」，复审者独立解读输出、独立形成结论。
- **跨任务复用（R8，2026-09-07）**：新任务启动先查技能级可用积木清单 `~\.agents\skills\_shared\bricks\catalog.md/json`；可 import 的积木即用、不重写。独立性纪律与复用同（积木只编码「输入→确定性计算」、禁含预期结论，预期由当轮评审者独立形成）。

**阶段 L1（快筛）**：对象 ≤10 万字符（参数化）时通读全文一遍；超大对象只读目录结构与各章节首尾段做抽样快筛，禁止无差别全量读入。输出①可疑段落清单②风险热力图所需的便宜信号（引用密度、数字密度、L0 命中聚集度）。不深挖。

**阶段 L2（对抗深审）**：仅覆盖热力图高分区（score=prior×signal×impact，细则见 `references/protocols.md` 4.7，仅在需要时读取）。对抗视角默认三类：边界条件、交叉引用一致性、外部硬约束符合性。并行判据满足时才分子审查者，仲裁规则见 protocols.md 4.6。

**意见输出（必须遵守）**：每条意见必须给出 `anchor`（位置锚点）、`basis`（依据）、`confidence`；缺任一直接丢弃；禁止复制原文段落，引用一律用锚点；按严重度排序输出：阻断→严重→轻微→建议。**审查元信息（强制）**：每轮意见单头部须显示该轮 subagent 的 provider/model 与 reasoning_effort（未指定写"未指定·继承默认"），格式为表格行（轮次 | Provider/Model | Reasoning Effort）。

**落地核查（2026-11-01 追加，本机三次踩坑）**：
1. 审「生成物」前必须确认已重新渲染：模板/源文件改了不等于产物改了。核对产物 mtime 与关键字符串；未渲染就当"对象不存在"，先渲染再送审。
2. 审查结论只覆盖本轮对象：任何新改动都要重送审，禁止把上一轮"通过"当通行证。
3. 预演/试运行（DryRun 之类）一律不得写状态文件、不得影响真实状态——否则会把"没执行"记成"成功"。
4. 送审通道按 `$DSH_HOME/AGENTS.md` §7「对抗性审查的送审配置」执行：本地 GLM-5.3-Flash（zai/glm-5.3-flash）+ 外包 CodeBuddy；简单只送外包，复杂/重要双送并对拍。
## 3. 修复闭环（默认模式）

1. 审查前与用户确认通过判据（默认：阻断清零∧严重清零）并冻结；循环中不得加码。
2. 用 `scripts/ledger.py` 建台账；只有阻断/严重级进入修复循环。
3. 修复仅限台账列明项，**禁止顺手修改**；修复后按台账逐条验证。
4. 第二轮起：运行 `scripts/diff_scope.py` 取增量范围，只审 diff＋关联段＋未关闭台账项；已验证部分标记冻结区不重审。
5. **复审独立性**：复审（第二轮及以后）遵循 §2「审查执行独立性」——独立子审查者、只喂必要数据；额外**显式列出/排除同目录复审报告文件**（防止子审查者自读他人复审结论污染）；另把**上轮 L0 脚本**（不含结论断言）随上轮意见单一并喂给复审者并明确「可复用/扩展」——复审者独立解读输出、独立形成结论，不必重写既有确定性脚本。子审查者上下文净化不受净收益不等式约束（§5.3）；子审查者结论与上轮/主流程结论对拍，分歧项按 protocols.md 4.6 仲裁。
6. 收敛判定：两轮意见重合度 ≥0.80 且阻断清零 → 停止；超 5 轮 → 熔断，输出遗留清单交用户裁决。
7. 同一 issue 重开 ≥2 次 → 暂停并报告"修复规范可能不完整"，请用户裁决。

## 4. 仅报告模式

执行第 2 节后直接输出分级意见单与台账，不进入修复循环；用户后续可凭台账要求修复。

## 5. 费用控制（必须遵守）

1. 逐轮记录 token（输入/输出/命中，读不到记 null）。
2. 模型识别：识别当前模型 → 查 `references/pricing-models.md` 的 JSON 块取价格与峰谷；识别不到 → 用 default 行（λ=1/30）并明示"按默认系数估算"。
3. 压缩判定：压缩任何上下文前必须过净收益不等式（见 protocols.md 6.2）；**审查者子上下文的净化（截断/重构）不适用该不等式**——观测独立性优先。
4. 批量任务且处于高峰时段 → 给出峰谷费用差提示，由用户选择；用户即时指令优先。

## 6. 收尾（每轮完整运行必须执行）

1. 组装本轮快照（schema 见 protocols.md 7.1；含台账结论与逐轮 token 数字）→ `python3 scripts/collect_snapshot.py --ns <ns>`。
2. `python3 scripts/sediment_check.py` → 按信号行动：
   - 顶层 `signal` 字段为 `"sediment"`（按 JSON 字段解析判定；实际输出键值间有空格，勿做 `signal:"sediment"` 无空格子串匹配）：**先读顶层 `suppressed` 与 `signals[].signal=="suppressed"`**——若该命名空间已被 `var/overrides.json` 抑制，则按 `"none"` 处理、不启动沉淀（抑制是机械生效的，不得凭记忆推翻）；未被抑制才输出告示行（"已满足沉淀条件，启动静默迭代：命名空间 X，预计 ≤Y token/约 Z 元，输入'停止沉淀'可中断"）→ 跳转第 7 节沉淀流程；
   - 顶层 `signal` 字段为 `"remind"`：回复末尾附提醒一句（24h 内已提醒过则跳过）；
   - `"none"`：无动作（但 `signals` 里有 `suppressed` / `override-expired` 时，须在回复中一行说明，禁止静默）；

## 7. 沉淀流程

1. **触发**：静默（信号）/提醒（用户同意）/显式（"执行沉淀"）。显式命令先扫描各技能根（Kimi 用户技能目录、`~/.agents/skills`、`$DSH_HOME/skills`、`~/.workbuddy/skills`，按宿主实际存在的根）下所有 SKILL.md 的 frontmatter，列出含 `sediment: true` 的技能＋全部＋取消，用户确认后执行。
2. **执行**：`python3 scripts/sediment_run.py --ns <ns>` 按 S0→S6 分阶段。脚本先产出 S2 候选清单（`var/sediment/iter-N-candidates.json`）并停在该阶段等你裁决：由你撰写新条款文本并做语义裁决（降权/淘汰/合并），再以 `--guide-edits <裁决文件>` 续跑完成 S2 及后续阶段（脚本落盘）；裁决文件是 JSON：`{"add":[{"ns":"document","line":"- [D-003] …"}],"demote":["D-001"],"retire":["D-002"]}`。分阶段落盘（每阶段写 checkpoint），可断点续，可中断。
3. **可见性**：开始前一行告示（预计消耗）；思维链可见宿主在思维链声明；完成后末尾一行总结。
4. **预算**：受第 1 节参数约束；超限即截断，剩余留队。
5. **条款生命周期（M1/M7，owner 裁决 2026-09-10）**：条款状态存 `var/registry/guide-clauses.json`（**注入端不读它，零成本**）。新条款一律先入 `trial`，观察 `TRIAL_WINDOWS_REQUIRED=2` 个沉淀窗口：有实际返工证据（`basis` 非空）才升 `active`；试用到期无正面证据 → 转"淘汰建议"（保守取向：无法证明有效即不固化）。`active` 条款**零证据窗口**连续 2 窗 → 降权建议，连续 4 窗 → 淘汰建议（零证据＝本窗口既无引用又无绑定证据）。**文本改动一律由 agent 裁决后经 `--guide-edits` 落盘，脚本不自动改条款文字。** 每轮变更同时落审计文件 `var/sediment/iter-<N>-guide-changes.json`（裁决原文＋实际生效/被拒条目＋生命周期结论＋本轮被截断条款），使"凭什么改条款"可追溯。
6. **反自我强化纪律（M2~M6，必须遵守）**：本技能存在一条真实的自反馈回路——生成端按导引单写 → 审查端读同一份导引单（`references/namespaces/*.md` 显式映射导引单条款）→ 意见天然对准条款 → 命中率虚高 → 条款被"证明"有效而固化。**同源污染不可当有效性证据。** 五条纪律：
   - **M2 命中率只作"参与度线索"，不得作为条款存废判据**（也不参与升格）。零命中单独**不得**产出降权候选——只产出 `demote-hint` 线索；累计达 `ZERO_EVIDENCE_DEMOTE` 窗口才产出 `demote-candidate`。零证据窗口的**复位**条件是"本窗口该条款有引用（hits>0）**或**有绑定返工证据（`basis` 非空）"；`hits` 只能复位、**不能**用于 `trial→active` 升格（升格只认 `basis`），故同源污染被限制在"最多让条款避免被淘汰"这一上界内，无法把条款"证明成有效"。**零命中 ≠ 无效**：条款被遵守恰恰表现为零命中，把它当无效淘汰是反向误杀。
   - **M3 新增候选须双向达标**：近窗口该类型 ≥`new_threshold`(=5) 次 **且** ledger 中该类型曾有 issue 实际进入修复流程（仅"提出过"不算——提议会被驳回，只有真动手修过才产生返工成本）。只满足频次的产出 `new-clause-rejected` 留痕，不生成候选。
   - **M4 条款数上限**：通用 ≤10 ∧ 每命名空间 ≤4（由 600 token 预算反推，`guide_inject` 实测 10+4 约 493 token）。到上限后新增**必须先淘汰等量**，否则 `apply_guide_edits` 拒绝该 add 并记入 `skipped`。防"只增不减"。
   - **M5 被预算截断的条款不得进降权候选**：其"零命中"是结构性的（它根本没被注入），不是有效性证据。`guide_dropped` → `demote-suppressed`。
   - **M6 条款文本须可客观检验**：含不可证伪措辞（认真/重视/尽量/尽可能/严格/加强/提高意识）→ **确定性拒绝**；未识别到可检验对象（位置/字段/数值/编号/条款号）→ 放行但出 `warn`，由 agent 人工确认可验证性（启发式不做硬门，避免误杀）。

## 附：脚本执行与状态目录

- 脚本一律 Python 3.9+ 标准库、零第三方依赖，均以 `__file__` 自定位技能根，**与当前工作目录无关**，可在任意位置以绝对/相对完整路径调用；失败时输出 `{"error":…,"hint":…}` 单行 JSON 并退出非 0 码，必须如实转告用户，禁止静默跳过。公开入口六个：`collect_snapshot` / `diff_scope` / `guide_inject` / `ledger` / `sediment_check` / `sediment_run`（`scripts/` 下 `_` 前缀文件为内部模块，不单独调用；另有 `scripts/tests_node/` 自测入口，均不计入"公开入口"口径）。
- 状态目录三级回落（解析顺序）：环境变量 `ADV_REVIEW_HOME`（用户显式指定优先）→ `<技能根>/var/`（可写时）→ `~/.adversarial-review`（保底）。各脚本均支持 `--state-dir` 覆盖状态目录（主要供测试/演示隔离）。
- **编码纪律（2026-09-10 实测踩坑）**：`var/overrides.json` 等**由 agent 而非 Python 落盘的 JSON**，读取端一律按 `utf-8-sig` 解析——Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写入 BOM，按 `utf-8` 读会直接抛 `Unexpected UTF-8 BOM` 使整条抑制功能失效。Python 落盘的 JSON 由 `save_json` 写为 UTF-8 无 BOM。
